# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v17 (2026-11-24)

Status: Draft for 0012-W4 v1. Replaces [sync v16](0003-sync-v16.md), whose rules remain in force word for
word except as below. [Document v21](0001-document-v21.md) adds the **video** object type (keys `asset`,
`poster`, `pixelWidth`, `pixelHeight`, `durationMs`, `name`, `description`) and schema version **15**. This version moves
the room's live board to 15 and lets a team board hold video objects once the room holds both the video and its
first frame. The room's storage version stays **9** ([hosted storage v14](0003-hosted-storage-v14.md)).

## Schema version 15 in the room

A room's **live** board is always version 15. Every rule sync v15 gives for version 14 (pages in `pageMap`, the
object map's `page` key, tables) applies to version 15. Version 15 differs from 14 only in allowing video objects.
This section is the one place that says which schema versions each input accepts; document v21 points here.

**Decoded type.** Because document v21 makes `BoardV14` an alias of `BoardV15`, `readBoard(doc, legacy?)` in
`packages/board-sync/src/codec.ts` no longer claims it. It returns a new exported **`DecodedBoard`**: the union of
document v21's board shapes for versions 10 to 15, exactly as stored, unpaged for 10–12 (no `pages`, no object
`page`) and paged for 13–15 (`pages` and every object's `page`). Its paged versions become 13, 14 and 15. A new
**`readLiveBoard(doc): BoardV15`** calls `readBoard(doc)` and throws `Error("invalid_update")` unless the version is 15.

| Caller | Reads with | Allowed change |
| --- | --- | --- |
| `packages/board-sync/src/session.ts` (the `board` getter) | `readLiveBoard` | Runtime call changed from `readBoard` |
| `packages/board-sync/src/undo.ts` (the state reader) | `readLiveBoard` | Runtime call changed from `readBoard` |
| `packages/board-room/src/edits.ts` | `readBoard`, unchanged | Its schema check after `validate` expects 15 and stays in the `invalid_document` branch: a well-formed edit of another version is `invalid_document`, a malformed map `invalid_update`, as today |
| `packages/board-room/src/room.ts` load and `upgradeStored`; `history.ts` backup verification | `readBoard` | Narrow to `BoardV15` after upgrading |

**Input matrix.** Every input keeps exactly this range; each is validated at its declared version (so a version 14
document holding a video is `invalid_document`), then upgraded to 15 by document v21's `upgrade` before it is
persisted or served:

| Input | Versions accepted, with their page layout |
| --- | --- |
| A client update, and the live board after any edit | 15, `pageMap` |
| A stored room at load, storage 7 (`readBoard(doc, true)`) | 10–12 unpaged, or 13 with a live `pages` value |
| A stored room at load, storage 8 or 9 | 10–12 unpaged, or 13–15 with `pageMap` |
| A history version's document (`documentBytes`: previews, restore, capture comparison) | 10–15 (JSON; 13–15 with `pages`) |
| A backup's snapshots and replayed head (`validateHistoryBackup`), storage 7 | 10–12 unpaged, or 13 with a live `pages` value |
| The same, storage 8 | 10–12 unpaged, or 13–14 with `pageMap` |
| The same, storage 9 | 10–12 unpaged, or 13–15 with `pageMap` |
| A created board (`room.ts`) and an imported board (`routes/boards.ts`) | 13–15 |
| Team template objects (`templates.ts`) | Validated inside a version 15 wrapper |

A backup head of storage 7 or 8 holds no image and no video (hosted persistence v12).

**Stored rooms upgrade when they load,** in one shared-document transaction, whenever the stored version is not 15:

| Stored room | Upgrade |
| --- | --- |
| Schema 10–12 (any storage), or storage 7 with schema 13 | The existing steps (`upgradeStored`: pages, then `pageMap`), then the schema-only step |
| Storage 8 or 9, schema 13 or 14 (`pageMap`) | The **schema-only step**: the board map's `schemaVersion` becomes 15. No other key is written |

The upgrade is not a person's edit: no edits row, receipt, revision or history version; the room writes the
snapshot at the unchanged current revision. `room.ts` creates new boards at 15 and its `upgradeStored` sets 15.
The transition check keeps a board's version fixed within an edit.

**History.** The automatic capture's legacy comparison (`history.ts`) gains version 14, so a version 14 capture
and its version 15 upgrade with no other change cause no new capture.

## Editing

Step 5's clause from sync v16 ("every image object that the edit adds … `asset_missing`") is replaced by:

> and **every image object that the edit adds, or whose `asset` it changes, refers to an asset the room holds as a
> picture**, and **every video object that the edit adds, or whose `asset` or `poster` it changes, refers by
> `asset` to an asset the room holds as a video and by `poster` to an asset the room holds as a first frame, that
> is with the type `image/jpeg`** (hosted storage v14's held predicate). A poster held with any other picture type
> is refused. An image or video whose id was on the board before the edit, as the same type with the same `asset`
> (and, for a video, the same `poster`), is not checked. Otherwise the edit is `refused` with the reason
> **`asset_missing`**. Nothing is stored.

The check stays in `packages/board-room/src/edits.ts`, after every other step-5 check, and runs in the room's
ordered queue with every store's final step, clean-up and capture, so no asset can be stored or removed between
the check and the edit's write. A video upload's receiving part runs outside the queue but is invisible until its
final step (hosted storage v14), so it never changes this check's answer.

So a board that holds a video whose video or first frame is missing still takes every other edit, rename,
deletion of that video, Duplicate of other objects and Undo or Redo of other steps; what is refused is adding such
a video again, or changing its `asset` or `poster` to one the room does not hold so.

A client sends an edit that adds a video only after its first frame's upload and then the video's upload to this
board answered 200 or 201 ([API v14](0003-api-v14.md)), or for a video copied (Paste, Duplicate) or restored
(Undo, Redo) on the same board, which uploads nothing ([interaction v50](0001-interaction-v50.md)). An
`asset_missing` refusal takes the existing refused-edit path in `packages/board-sync/src/session.ts` (the
`refused` branch: the request is marked refused, its deadline cancelled, the session drops with `refused_edit` and
rejoins), with no new client handling.

## Undo, Redo and history

Hosted Undo and Redo restore video objects as they restore images: the step holds the object's document keys,
never file bytes, and no upload is made. A video and its first frame stay held while a version, the live board or
a recent upload refers to them ([hosted persistence v12](0003-hosted-persistence-v12.md)); if either was removed,
the step is refused with `asset_missing` through the path above.

Version previews, version restore and the history list read videos like any other object. A version restore is
never refused for an asset the room does not hold: a video whose first frame is missing shows the web app's
missing-picture box, and one whose video is missing shows its first frame and fails to load when someone presses
play (interaction v50). Neither is checked by later edits that leave it as it is.

## The codec

`readBoard` reads a video's keys through the type registry, as it reads every type's. In the document adapter
(`packages/board-sync/src/document-adapter.ts`), stale keys are removed in one place only: the object loop of its
board writer, **after** the table branch has returned (a table's object map is written by `writeTable` and never
touched by this removal) and never on the board map or a `pageMap` entry (a page's `name` lives there and is
untouched). In that place:
- a **video** keeps `asset`, `poster`, `pixelWidth`, `pixelHeight`, `durationMs`, `name` and `description` and
  loses `text`, `style`, `marks`, `ends` and `connectorStyle`;
- an **image** keeps its keys as today and loses `poster`, `durationMs` and `name` as well;
- every **other** non-table type loses `asset`, `pixelWidth`, `pixelHeight`, `description`, `poster`,
  `durationMs` and `name`, as it loses the first four today.

This removes `name` only from object maps: a page's `name` lives in its `pageMap` entry and a table's maps are
written by `writeTable`, and neither is touched.

No frame, presence key, comment, vote or timer rule changes. A video is one object for presence selections,
comment anchors and vote targets (`voting: true`). Playing a video sends nothing: no frame, presence key or edit.
Files never travel in a socket frame: the 1 MiB message limit and the 2 MiB stored document limit are unchanged,
and a video adds only its document keys to them.
