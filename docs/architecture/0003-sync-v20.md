# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v20 (2026-11-27)

Status: Draft for 0011-W3 v1. Replaces [sync v19](0003-sync-v19.md), whose rules remain in force word for
word except as below; v19's text is kept here in full, with its version numbers moved on only where this version
requires it. [Document v24](0001-document-v24.md) adds **merged cells** (a table's `merges`: each merge is
`{ row, column, rows, columns }`, the ids of its top-left cell, its **anchor**, and how many rows and columns it
covers, counted from the anchor in the table's current order) and schema version **18**. This version moves the
room's live board to 18, stores a table's merges in a new `mergeMap`, says how moves and duplicates write order
keys, how concurrent merges, moves and inserts resolve, how hosted Undo restores merges, and what a client does when
a remote merge covers the cell it is editing (section **Merged cells**). The room's storage version stays **9**
([hosted storage v15](0003-hosted-storage-v15.md)); no frame, presence key, socket message or service table is
added.

**What changed from v19, in short:**
- **Schema version 18 in the room** (was 17): the live board, both `edits.ts` guards, the input matrix, created and
  imported boards, stored-room upgrades and history's legacy comparison move on by one. The stored-room upgrade that
  v19 called the schema-only step is now the **schema step**: it also gives every table's object map an empty
  `mergeMap`.
- **Merged cells** (new section): a table's `mergeMap` (key `<row id>:<column id>` of the anchor, plain value
  `{ rows, columns }`); how the codec reads it and `writeTable` writes only the entries that differ; a merge empties
  the covered cells' texts in the same transaction and a split deletes the entry; moves write one order key per moved
  id through `TableOrderHint.moved`, and duplicates write the copies' keys like an insert; the concurrency rules
  (arrival order, `promote()` extended to `mergeMap`, a result accepted only while document v24's merge rules hold);
  hosted Undo of `mergeMap` entries (every touched merge removed before texts are restored); a client that keeps its
  last valid board (`capture()` never emits a board that fails the rules; a valid remote `update` or own `saved`
  reconciles history and releases the hold, and refusal or failed reconciliation rejoins); and the notice for a
  remote merge over the cell being edited, shown only when the update added or changed the covering merge.
- **Links in text**: the codec's link check runs at version 17 or 18 (v19: 17); nothing else in that section changes.
- **Verification**: this version's checks added.

v19 itself replaced sync v18: [document v23](0001-document-v23.md) adds **links in text** (an optional `link` on a
mark of a rich-text object, checked by the link address rule `linkAddress`) and schema version **17**. v19 moved the
room's live board to 17, let the codec read and write a mark's `link`, refused an update whose marks hold an invalid
link, kept valid links through the room's repair, and made each link change one synced edit; its rules for links
stay.

v18 itself replaced sync v17: [document v22](0001-document-v22.md) adds the **link** object type (a **link card**: keys `url`,
`title`, `description`, `site`, `asset`, `layout`, `state`, `requestedAt`) and schema version **16**. v18
moved the room's live board to 16, let a team board hold link cards whose thumbnail the room holds as a picture,
and made a card's **arrival** (the one edit that fills in a pasted card) part of the paste's own Undo step; its rules
for link cards stay.

v17 itself replaced [sync v16](0003-sync-v16.md) and added the **video** object type (keys `asset`, `poster`,
`pixelWidth`, `pixelHeight`, `durationMs`, `name`, `description`) and schema version 15; its rules for videos stay.

## Schema version 18 in the room

A room's **live** board is always version 18. Every rule sync v15 gives for version 14 (pages in `pageMap`, the
object map's `page` key, tables) applies to versions 15, 16, 17 and 18. Version 15 differs from 14 only in allowing
video objects, version 16 from 15 only in allowing link cards, version 17 from 16 only in allowing a `link` on marks,
and version 18 from 17 only in a table's `merges` (in the shared document, its `mergeMap`: **Merged cells**). This
section is the one place that says which schema versions each input accepts; document v24 points here.

**Decoded type.** Because document v24 makes `BoardV14` to `BoardV17` aliases of `BoardV18`,
`readBoard(doc, legacy?)` in `packages/board-sync/src/codec.ts` claims none of them. It returns the exported
**`DecodedBoard`**: the union of document v24's board shapes for versions 10 to 18, exactly as stored, unpaged for
10–12 (no `pages`, no object `page`) and paged for 13–18 (`pages` and every object's `page`; version 14 built from
`StoredItemV14`, version 15 from `StoredItemV15`, versions 16 and 17 from `StoredItemV16` (`StoredBoard<16,
StoredItemV16>` and `StoredBoard<17, StoredItemV16>`, each with `pages`; their tables have no `merges`), version 18
being `BoardV18`). Its paged
versions become 13, 14, 15, 16, 17 and 18. **`readLiveBoard(doc): BoardV18`** calls `readBoard(doc)` and throws
`Error("invalid_update")` unless the version is 18.

Otherwise the returned type follows `readLiveBoard`; the arrival rule below |

Both stay in the `invalid_document` branch: a well-formed edit of another version is `invalid_document`, a malformed map `invalid_update`, as today (order of checks: **Links in text**) |

**Input matrix.** Every input keeps exactly this range; each is validated at its declared version (so a version 14
document holding a video, a version 15 document holding a link card, a version 16 document holding a mark with a
`link`, or a version 17 document whose table has `merges`, is `invalid_document`). **Upgrade on read applies only to
what becomes the live board**: a stored room adopted at load, a created or imported board, and a version restore are
upgraded to 18 by document v24's `upgrade` before they are persisted or served as the live board. A history
version's document served as a **preview**, the capture comparison, and a backup's snapshots and replayed head are
only validated: they keep their **declared versions** (`documentBytes` returns the document as stored and a preview
serves it so, as today), so a version 17 history version is previewed at 17:

A backup head of storage 7 or 8 holds no image, no video and no link card ([hosted persistence v13](0003-hosted-persistence-v13.md); a link card needs
version 16, which storage 8 never holds).

**Stored rooms upgrade when they load,** in one shared-document transaction, whenever the stored version is not 18:

| Stored room | Upgrade |
| --- | --- |
| Schema 10–12 (any storage), or storage 7 with schema 13 | The existing steps (`upgradeStored`: pages, then `pageMap`), then the schema step |
| Storage 8 or 9, schema 13, 14, 15, 16 or 17 (`pageMap`) | The **schema step**: the board map's `schemaVersion` becomes 18, and every table's object map gains the key `mergeMap` holding a new empty shared map (a stored table before 18 never holds one). No other key is written |

The upgrade is not a person's edit: no edits row, receipt, revision or history version; the room writes the
snapshot at the unchanged current revision. `room.ts` creates new boards at 18 and its `upgradeStored` sets 18 and
adds the empty `mergeMap`s. The transition check keeps a board's version fixed within an edit.

**The byte cap on a legacy board.** Document v24's 2,097,152-byte canonical payload cap is checked on the **stored**
form only when loading a stored legacy room: `room.ts` checks `canonical()` at the stored schema before
`upgradeStored`. The `merges: []` the upgrade adds to each table is **not counted** on that read or on the upgrade.
Only this load-time upgrade uses the uncapped path in `snapshots.ts`, so a stored room at the cap still loads
and writes its upgraded snapshot at the same revision. A server create, import or restore is a write:
its upgraded schema 18 payload is measured and refused above the cap with the existing words.
Every later edit checks the upgraded form as today: an edit whose result is over
the cap is refused with `document_too_large` (`edits.ts`, the existing words), so the first edit of such a room that
does not shrink it may be refused. The history version limit (2,162,688 stored bytes, `history.ts`) is unchanged and
far above what the added keys can add (at most 250 tables).

**History.** The automatic capture's legacy comparison (`history.ts`) gains version 17 (it compares 10 to 17), so a
version 17 capture and its version 18 upgrade with no other change cause no new capture (v19 added version 16, and
v18 version 15, in the same way). Every older form of version 14 to 17 leaves out each table's `merges`, and **no
older form is built while any table has a merge** (a board holding a merge has no valid form before 18, as one
holding a link card has none before 16), so adding the first merge always counts as a change.

## Editing

Step 5's clause from sync v16 ("every image object that the edit adds … `asset_missing`") is replaced by:

> and **every image object that the edit adds, or whose `asset` it changes, refers to an asset the room holds as a
> picture**, and **every video object that the edit adds, or whose `asset` or `poster` it changes, refers by
> `asset` to an asset the room holds as a video and by `poster` to an asset the room holds as a first frame, that
> is with the type `image/jpeg`** (hosted storage v14's held predicate), and **every link card that the edit adds
> with a non-null `asset`, or whose `asset` it changes to a non-null value, refers to an asset the room holds as a
> picture, of any picture type** (the same predicate as an image's). A poster held with any other picture type
> is refused. An image, video or link card whose id was on the board before the edit, as the same type with the
> same `asset` (and, for a video, the same `poster`), is not checked; a card whose `asset` is `null` is never
> checked. Otherwise the edit is `refused` with the reason **`asset_missing`**. Nothing is stored.

The check stays in `packages/board-room/src/edits.ts`, after every other step-5 check, and runs in the room's
ordered queue with every store's final step, clean-up and capture, so no asset can be stored or removed between
the check and the edit's write. A video upload's receiving part runs outside the queue but is invisible until its
final step (hosted storage v14), so it never changes this check's answer. The objects it walks are those that hold
an asset (`assetsOf(o).length > 0`, document v22), not only `isMedia` ones.

The same typed check is `requireHeldMedia(objects, typeOf)` in `packages/board-room/src/room.ts`, used by a staged
import's claim and create (hosted storage v15) and by team templates (`apps/server/src/templates.ts`): for a link
card with a non-null `asset` it requires `typeOf(asset)` to be a picture type, else 400 `asset_missing`; a card whose
`asset` is `null` passes.

So a board that holds a video whose video or first frame is missing, or a card whose thumbnail is missing, still
takes every other edit, rename, deletion of that object, Duplicate of other objects and Undo or Redo of other steps;
what is refused is adding such an object again, or changing its `asset` or `poster` to one the room does not hold
so.

A client sends an edit that adds a video only after its first frame's upload and then the video's upload to this
board answered 200 or 201 ([API v14](0003-api-v14.md)), or for a video copied (Paste, Duplicate) or restored
(Undo, Redo) on the same board, which uploads nothing ([interaction v50](0001-interaction-v50.md)). A client sends
the **arrival** edit that gives a card its `asset` only after the thumbnail's upload to this board
(`PUT /boards/:board/assets/:hash`) answered 200 or 201; a card copied (Paste, Duplicate) or restored (Undo, Redo)
on the same board uploads nothing ([interaction v52](0001-interaction-v52.md)). An `asset_missing` refusal takes
the existing refused-edit path in `packages/board-sync/src/session.ts` (the `refused` branch: the request is marked
refused, its deadline cancelled, the session drops with `refused_edit` and rejoins). For an arrival's request the
paster's browser then follows **One retry** (below), and nothing else.

## Link cards: paste, arrival and the 20,000 ms rule

A pasted card is written in **two edits**, both by the paster's browser:
1. **The paste** adds the card with `state: "loading"`, empty texts, `asset: null`, `layout: "vertical"`, the
   loading size and `requestedAt` (document v22). It is one ordinary Undo step.
2. **The arrival**, when the preview answer and the thumbnail's storage are done (interaction v52), changes only that
   card, and only its **finish keys**: `title`, `description`, `site`, `asset`, `state` (`"ready"` or `"linkOnly"`),
   `layout`, `width` and `height`. The paster's browser builds it from the card as its board holds it at the commit,
   so `x` and `y` are those it then holds (a move made while the card loaded is kept), changed only when the new size
   would cross the document bounds (shifted left and/or up just enough, interaction v52). No other key changes. The
   document adapter stores a rectangle as **one** shared value, `geometry` (`{ x, y, width, height }`), and the
   finish keys as their own keys; the adapter's single transaction writes `geometry` (when it differs) and every
   changed finish key together, so the arrival is **one update**. It is written only when interaction v52's gate
   passes (the same board opening, the active local writer or the live editable document, an owner or editor, and a
   card with the paste's `id`, `url` and `requestedAt` still on the board with `state: "loading"`); otherwise nothing
   is written (the card was deleted, undone, changed back to text or restored under a fresh `id`), and an uploaded
   thumbnail no object names is cleared by the existing clean-up of unreferenced pictures (hosted storage v15;
   [storage v5](0001-storage-v5.md) on single-user boards).

**Concurrent edits to a card. Amendment A5 (2026-11-25).** Document v22 accepts any card size with any state, so the merge of an edit that
writes a card's `geometry` with an edit that writes its other keys is always a valid card. In particular, when another
person moves the card concurrently with its arrival (neither client had seen the other's edit), the two `geometry`
values conflict. The room's existing `promote()` in `packages/board-room/src/conflicts.ts` keeps the `geometry`
that the room accepts last in its save order, regardless of the Yjs client IDs. Both outcomes are **accepted** and
neither is refused or repaired:
- arrival accepted last: the card is finished at the place the paster's board held, and the move is lost;
- move accepted last: the card is finished at the moved place and keeps the loading size, 306 × 288 (a
  valid card size), and every client draws its face inside that rectangle (interaction v52).

The same holds for a move concurrent with a layout choice. A concurrent merge that breaks another document rule (for
example the state-and-keys table) is refused by the room's existing document check, as any invalid merge is today.

Viewing, copying, Duplicate, Undo, Redo, version restore, files and templates never send a preview request and never
write an arrival. A card whose arrival never comes stays `loading` in the document; every client draws and treats it
as link-only once its own clock is 20,000 ms or more past the card's `requestedAt` (document v22 link rule 5), and
nothing is written for that. Other people on the board see the loading card from the paste and the finished card
from the arrival, as ordinary remote edits.

## Undo, Redo and history

Hosted Undo and Redo restore video objects and link cards as they restore images: the step holds the object's
document keys, never file bytes, and no upload or preview request is made. A video and its first frame, and a
card's thumbnail, stay held while a version, the live board or a recent upload refers to them
([hosted persistence v13](0003-hosted-persistence-v13.md); the room's referenced set is `assetsOf` of every object,
so it includes cards' thumbnails); if one was removed, the step is refused with `asset_missing` through the path
above.

**The arrival amends the paste's step** (`packages/board-sync/src/undo.ts`). `SharedUndo` gains
`amend(before: State, after: State, id: string): boolean`, which the paster's session calls for the arrival edit in
place of `record`.

**How an edit is known as an arrival.** Each step below takes one new optional last parameter, `arrivalOf?: string`
(the card's `id`); without it every function behaves exactly as today. The web client's `commit(input, recordObject,
orderIds?, opens?, movedPages?, tableHint?, arrivalOf?)` (`apps/web/src/state/use-board-document.ts`) passes it
through `apply` to `HostedBoard.edit(board, group?, movedPages?, page?, tableHint?, arrivalOf?)`
(`apps/web/src/team/hosted-board.ts`), which passes it through its existing `deliberate` to
`BoardSession.edit(board, group?, movedPages?, page?, tableHint?, arrivalOf?)`, which passes it to `write`. `write`
captures `before`, sets the board as today, and then calls `this.history.amend(before, capture(this.doc), arrivalOf)`
instead of `this.history.record(…)`, and passes `arrivalOf` to `sendEdit(update, group?, touched?, arrivalOf?)`. An
arrival commit records nothing in the web client's own history and uses no edit group. Undo and Redo never pass
`arrivalOf`.

**The request carries it before dispatch.** The session's `Request` type gains `arrivalOf?: string`. `sendEdit` puts
`arrivalOf` on the request object **when it creates it, before it stores it in `requests`, before the size check and
before `sendRequest`**. So every refusal of that request is matched to the card, including the **synchronous** one:
`sendEdit` refuses a message above 1,048,576 bytes at once (it marks the request refused, drops with `refused_edit`,
rejoins and reports `{ kind: "refused", requestId, reason: "message_too_large" }`) before `edit` has returned. The
deadline, refusal and resend handling are otherwise exactly today's. `HostedBoard.changed`, for a `refused` event
whose `requestId` names a request with `arrivalOf` (read from `session.requests`), runs today's refusal branch
without the toast (`this.spotlight.clear(); this.clearPresence(); this.publish({ connected: false })`; no
`words.refusedEdit`) and notes the refused card id; every other event is unchanged. `HostedBoard.edit` keeps its
result exactly as today: `false` when not admitted (cannot edit, no session, or no change), otherwise `deliberate`'s
result (`true` once the session made a request, even one refused at once, or the session's reason string). A new
method `HostedBoard.arrivalRefused(id: string): boolean` answers `true` once for each noted card id (and forgets it),
else `false`.

**One retry.** This is the only rule for a refused arrival, on every path. When an arrival's edit is refused (matched
as above), the paster's browser makes **exactly one** further arrival for that card, the **link-only finish**,
silently: after the board has rejoined, when interaction v52's gate passes and its holds have cleared, if the card is
still on the board in `state: "loading"` with the same `id`, `url` and `requestedAt` and the 20,000 ms deadline
allows (a finish past it is the link-only finish anyway). It is committed as an arrival (`arrivalOf`), so it too is
part of the paste's step. If that retry is refused as well, or the card is no longer loading, nothing more is
written: the card stays `loading` and is drawn link-only once document v22's 20,000 ms have passed. No toast or
notice shows for either refusal.

**`amend(before, after, id)`:**
1. It first calls `observe(before, after, true)`, as `record` does, so the arrival is the connection's own edit for
   every step's guards: every live `object` entry refreshes its guard (as today for own edits), and a live unit entry
   refreshes its guard only when its `after` equals the unit's new value (as today). So a later step of this
   connection whose entry holds a unit the arrival changed keeps its old guard and is **stale**: a move made while the
   card loaded has a `geometry` entry (`x`, `y`, `width`, `height` together) whose `after` holds the loading size, so
   when the finish changes the card's size that entry is stale. Undo of that step follows the existing rule: only its
   entries whose guards still hold are reverted, and when none holds, Undo answers `changed_by_others` (today's
   notice) and the step is gone. When the finished size equals the loading size (306 × 288), the adapter writes no new
   `geometry` and the move undoes as usual.
2. It looks for the newest step in `past` holding a live entry `{ id, key: "object", before: null }` (the paste that
   added the card). If there is one, it sets that entry's `after` to its old value with the finish keys (`title`,
   `description`, `site`, `asset`, `state`, `layout`, `width`, `height`) taken from the card in `after`, keeping the
   old value's `x`, `y`, `order` and every other key (`x` and `y` shifted left and/or up just enough when the new
   size would cross the document bounds), and returns `true`. Otherwise it returns `false`.
3. Either way it adds **no step**, leaves `future` and the current edit group as they are, and the arrival is never an
   undo step of its own: no Undo or Redo ever reverts it.

So the outcomes are (each checked under **Verification**):
- **paste → arrival → Undo → Redo:** the paste's step, its guard refreshed by step 1, removes the finished card;
  Redo's step is computed from the board as Undo left it (as today), so Redo restores the finished card, under a
  fresh `id` (as every hosted restore).
- **paste → move → arrival → Undo → Undo → Redo → Redo:** when the finish changed the size, Undo 1 answers
  `changed_by_others` and the move's step is gone; Undo 2 removes the finished card; Redo 1 restores it finished at
  its moved place under a fresh `id`; Redo 2 has nothing to redo. A move made during loading may therefore no longer
  undo after the arrival: accepted.
- **paste → Undo before the arrival:** the card is removed; the arrival finds no card and writes nothing. Redo
  restores the loading card under a fresh `id`, which no arrival ever finds: it stays `loading` (no new request) and is
  drawn link-only once 20,000 ms are past its `requestedAt`.
- **paste → Change back to text → Undo → arrival (hosted):** the conversion removed the card and Undo restored it
  under a fresh `id`, so the arrival's gate finds no card with its `id`, uploads nothing if it has not yet uploaded,
  and writes nothing (the arrival is **dropped**); the restored card stays `loading`, follows the 20,000 ms rule and
  is never fetched again. (On a single-user board the same sequence **applies** the arrival, because local Undo
  restores the same `id`: interaction v52 and web modules v50.)
- **a concurrent move by another client and the arrival:** both outcomes under **Concurrent edits to a card**.

Another person's steps are unaffected beyond today's rule: for them the arrival is a remote edit, which kills their
entries for the units it assigned, as any remote edit does. The single-user board's local history follows
interaction v52 and web modules v50 instead (its restores keep the card's `id`).

Version previews, version restore and the history list read videos and link cards like any other object, and
marks with links like any other marks. A version
restore is never refused for an asset the room does not hold: a video whose first frame is missing, or a card whose
thumbnail is missing, shows the web app's missing-picture box, and one whose video is missing shows its first frame
and fails to load when someone presses play (interaction v50). Neither is checked by later edits that leave it as it
is. A restored `loading` card stays `loading` and follows the 20,000 ms rule.

## The codec

`readBoard` reads a video's keys and a link card's keys through the type registry, as it reads every type's. A
card's `asset` is stored in its object map as the hash or as `null`; an absent `asset` key reads as `undefined`, which
document v22 refuses. In the document adapter (`packages/board-sync/src/document-adapter.ts`), stale keys are removed
in one place only: the object loop of its board writer, **after** the table branch has returned (a table's object
map is written by `writeTable` and never touched by this removal) and never on the board map or a `pageMap` entry (a
page's `name` lives there and is untouched). In that place:
- a **video** keeps `asset`, `poster`, `pixelWidth`, `pixelHeight`, `durationMs`, `name` and `description` and
  loses `text`, `style`, `marks`, `ends` and `connectorStyle`, and also `url`, `title`, `site`, `layout`, `state`
  and `requestedAt`;
- an **image** keeps its keys as today and loses `poster`, `durationMs` and `name` as well, and also `url`,
  `title`, `site`, `layout`, `state` and `requestedAt`;
- a **link card** keeps `url`, `title`, `description`, `site`, `asset`, `layout`, `state` and `requestedAt` and
  loses `text`, `style`, `marks`, `ends`, `connectorStyle`, `pixelWidth`, `pixelHeight`, `poster`, `durationMs` and
  `name`;
- every **other** non-table type loses `asset`, `pixelWidth`, `pixelHeight`, `description`, `poster`,
  `durationMs` and `name`, as it loses the first four today, and also `url`, `title`, `site`, `layout`, `state` and
  `requestedAt`.

This removes `name` and `title` only from object maps: a page's `name` lives in its `pageMap` entry, the board's
`title` in the board map, and a table's maps are written by `writeTable`, and none of them is touched.

No frame, presence key, comment, vote or timer rule changes. A video is one object for presence selections,
comment anchors and vote targets (`voting: true`); so is a link card (`voting: true`). Playing a video sends
nothing: no frame, presence key or edit. Opening a card's link sends nothing to the room either. A preview request
is an HTTP call to the server ([API v16](0003-api-v16.md)), never a socket frame. Files never travel in a socket
frame: the 1 MiB message limit and the 2 MiB stored document limit are unchanged, and a video or a link card adds
only its document keys to them.

## Links in text

**The codec.** `readBoard` reads each mark of a text-bearing object's `marks` value with
`exact(mark, ["start", "end", "bold", "italic", "strike", "link"])` (v18: without `link`), so `link` is the one key
a mark gains. **Only when the board map's `schemaVersion` is 17 or 18** (v19: 17), before it returns, it throws
`Error("invalid_update")` for a mark whose `link` is present and:
- is not a string; or
- is not accepted **unchanged** by document v23's link address rule (`linkAddress(link)` from
  `packages/board-rules/src/text-link.ts` must answer `{ ok: true, href }` with `href === link`).

At any other version the codec does not look at a `link`'s value; the version rules below refuse it.

**Order of checks for a client update** (`packages/board-room/src/edits.ts`), first refusal wins; nothing is stored:
1. `readBoard`: a malformed map, an unknown key in a mark (`exact`), and, at version 17 or 18, a non-string `link` or
   one the address rule does not accept unchanged → `invalid_update`.
2. The version guard right after `readBoard` (`edits.ts:36`): any version other than 18 → `invalid_document`. So a
   version 16 update holding a mark with a `link`, valid or not, is `invalid_document` (the version rule first), as
   the input matrix says, and so is a version 17 update whose links pass step 1.
3. The page check, then `repair` (below), as today.
4. `validate` (document v24; for marks document v23's order: keys, values, `validExtras`, style, then marks) and the
   guard after it (`edits.ts:44`, 18) → `invalid_document`. This is where a `link` on an object that is not rich text is refused,
   even a well-formed one: a **connector** with a linked mark fails the connector's `validExtras` (its `marks` must be
   empty) and a `mindNode` fails `validMindNode`, each "Invalid object paint", before any link rule; a section fails
   the marks step ("Invalid marks"). `invalid_update` (step 1) is only for a malformed `link` value at version 17 or 18,
   whatever the object. `validate` also applies the address rule
   again, so no path stores a link it refuses.

Every other mark rule keeps today's path: repair normalises the marks before `validate`, and whatever is still
invalid is `invalid_document`. The document adapter (`packages/board-sync/src/document-adapter.ts`) writes each object's marks as
`o.marks.map(markOf)`, so with document v23's `markOf` a mark's `link` is written after `strike`; marks stay **one
atomic value** in the object map, as today.

**Repair.** `repair` (`packages/board-room/src/repair.ts`) is unchanged: it still sets, for every remaining
text-bearing object, `normalize(object.marks, count(object.text))` when that differs. With document v23's
`normalize`, links are kept as they are, cut to the merged text's length, and touching runs merge only when their
flags and their links are both equal. Repair never adds a link, never changes an address and never moves a link to
another object; it only drops the part of a link past the end of the merged text. As for flags today, a concurrent
text edit and marks edit (each `marks` value is written whole) may leave a link over shifted code points; the room
accepts that, as it does for bold.

**One synced edit per link change.** Setting, changing or removing a link ([interaction v53](0001-interaction-v53.md))
is one commit that changes only that object's `marks` value: **one** client update, one edits row and **one**
`SharedUndo` step (`record`), exactly as a bold toggle is. Undo and Redo of it restore the `marks` value as for a flag
change. Typing inside a linked text is a text edit whose remapped marks (document v23's `remap`) are part of that same
edit, as today. Copying a link, the hover card, following a link, copying a link to an object and the address bar
following the selection write **nothing** to the room: no edit, no undo step. Following a same-board link that
switches page sends the page in presence, as a page switch does today. No frame, presence key, comment, vote or timer
rule changes.

**Other inputs.** Created and imported boards, stored rooms, history versions, backups and team template objects
carry links in their marks as they carry flags; each is validated at its own version (input matrix), so a version 16
input holding a link is `invalid_document`. A version 13 to 17 input that becomes the live board (load, create,
import, restore) is upgraded to 18 by document v24's `upgrade`, which changes `schemaVersion` and gives every table
`merges: []` and nothing else (v19: only `schemaVersion`); history previews and backup inputs keep their declared
versions.

## Merged cells

Document v24's merge rules (`rows` and `columns` integers of at least 1 with at least 2 cells, the anchor a row and a
column of the table, the span inside the table counted from the anchor's index in the current order, no cell in two
merges, and no `cells` entry for a **covered** cell, that is a cell of a merge other than its anchor) apply to the
board as read, as every document rule does. Words used here: a row or column is an axis entry with a stable id; its
**index** is its place in the table's current order; a **span** is the indices a merge covers on one axis; a **run**
is rows (or columns) whose indices are consecutive.

### A table's object map at version 18

At version 18 a table's object map holds sync v15's live keys and **one more**:

| Key | Value |
| --- | --- |
| `mergeMap` | A shared map keyed by the anchor's **cell key** `<row id>:<column id>`. Each live value is a plain value `{ rows, columns }` (in that key order), one per merge |

A merge is **one plain value**: it is never a shared map, and its `rows` and `columns` are never written apart. At
versions 14 to 17 a table's object map holds exactly sync v15's keys; a `mergeMap` there, live or deleted, is
`invalid_update`. A covered cell keeps its (empty) shared text in `cells`: sync v15's initialization still gives every
live (row, column) pair a text.

### Reading

`readTable` in `packages/board-sync/src/codec.ts` receives the board's version (`readBoard` passes it; its accepted
versions become 10 to 18). At 18 its key list is sync v15's plus `mergeMap`, and the size check counts it. It refuses
with the existing `invalid_update`, in addition to sync v15's cases:
- a missing live `mergeMap`, or one that is not a shared map;
- a `mergeMap` key, live or deleted, that is not two lowercase UUIDs joined by `:` (the test `cells` keys pass);
- a live value that is not a plain value (prototype `Object.prototype`, as `place`) with exactly the keys `rows` and
  `columns`, each an integer.

It reads one merge `{ row, column, rows, columns }` for **every** live `mergeMap` entry, `row` and `column` taken from
its key. They are listed in canonical order: by the anchor row's index, then the anchor column's index. An entry whose
row or column is not a live `rowMap` or `columnMap` key is **not** ignored, unlike an orphan cell text: it is read
after the others, in key order (code unit), so that document v24's merge rules refuse the board. A covered cell's
non-empty text is read into `cells` as any cell's is, and is likewise refused. Every range rule (at least 1, at
least 2 cells, inside the table, no overlap, no covered text, anchor present) is document v24's and so is refused as
`invalid_document` by the room's step 4 (`validate`), never by the codec.

### Writing

`writeTable` in `packages/board-sync/src/document-adapter.ts` gains `mergeMap`:
- It creates `mergeMap` (an empty shared map) when the object map has none, as it creates `columnMap`, `rowMap` and
  `cells`.
- Its check for anything to write also compares the stored merges with the next table's `merges`, so a merge or a
  split alone is written.
- In the same transaction as the table's other writes, it deletes every live `mergeMap` key that is not the anchor
  key of a merge of the next table, and for each merge of the next table sets its key to `{ rows, columns }` **only
  where the stored value differs** (the `JSON.stringify` comparison `place` uses). An unchanged merge writes nothing.

So each step writes, in **one** update:
- **Merge.** The next table holds the new merge, has dropped the merges it replaced, and has no `cells` entry for a
  covered cell. The transaction sets the new entry, deletes each replaced merge's entry, and empties each covered
  cell's text that held text, by sync v15's grapheme-diff rule; the empty texts stay (texts are never deleted for
  being empty). The anchor's text is kept.
- **Split.** Deletes the entry. It writes no cell text of its own: the anchor keeps its text and the other cells are
  already empty.
- **Move** (a row, a column or a run, by menu or drag). The step's hint is `TableOrderHint` `{ table, axis, moved }`
  with `moved` the moved ids, the path an insert uses today. `writeAxis` passes `moved` to `orderWrites`, which keeps
  every stationary entry's key and gives **each moved id one new order key** between its new neighbours. As for every
  hinted write, sync v14's steps 5–7 still apply: when the stationary keys are not strictly increasing, `orderWrites`
  keeps the longest increasing set instead, and when no key fits between two neighbours it rebalances that axis of
  that table. On a fully initialized table (every live row and column pair has a text and no orphan text is live) whose stationary order keys are strictly increasing and where a key fits between each moved id's new neighbours, a move's update writes exactly one `order` per moved row or column and nothing else. A move writes no size, no cell text and no `mergeMap` entry of its own: ids are stable, a merge is
  counted from its anchor in the current order, and a move is offered only when it keeps every merge whole
  ([interaction v54](0001-interaction-v54.md)), so a merge inside a moved run moves with it.
- **Duplicate** (a row, a column or a run). The copies are inserted right after the run; the hint's `moved` is the
  copies' ids, so `orderWrites` gives the copies keys **between the run's last entry and the entry after it** (after
  the last key when the run ends the table), as an insert from a dot does. Each copy gets its entry with its size,
  one text per cell along the other axis (holding the copied text) and one `mergeMap` entry for each copied merge,
  keyed by the copy's anchor ids.
- **Insert** (a dot or a menu item). As today (`moved: [id]`); when the insert lands strictly inside a merge's span,
  that merge's entry is rewritten with its grown `rows` (or `columns`).
- **Delete a row or column.** As today; each merge it changes is rewritten: its `rows` (or `columns`) reduced, or,
  when the deleted row (column) held the anchor, the old key deleted and the new anchor's key set; a merge left with
  one cell has its entry deleted.
- **Clear several cells.** Each chosen cell's text emptied.

Sync v15's exception stands for every one of these steps: like any write of a table, it also initializes each missing
intersection with an empty text and deletes every orphan text in that table, in the same update. So the exact writes
above (a move's order keys only, a split's one deleted entry) are the whole update only for a **fully initialized**
table: every live (row, column) pair has a text and no orphan text is live. A table can lack that only after a
concurrent race (sync v15's **Concurrent changes**). The move's receipt, word for word wherever it is cited: On a fully initialized table (every live row and column pair has a text and no orphan text is live) whose stationary order keys are strictly increasing and where a key fits between each moved id's new neighbours, a move's update writes exactly one `order` per moved row or column and nothing else.

**Net writes** (sync v15's table, these rows added):

| Step | Its own writes | Also required |
| --- | --- | --- |
| Merging cells | One `mergeMap` entry set, the entries of the merges it replaces deleted, and every covered cell's text that held text emptied | — |
| Splitting a merged cell | One `mergeMap` entry deleted | — |
| Moving rows or columns | One `order` per moved row or column (the move's receipt above) | Other keys only when v14's steps 5–7 require (ties, rebalance), and sync v15's initialization and cleanup |
| Duplicating rows or columns | One entry per copy (order key and size), its texts, and one `mergeMap` entry per copied merge | As for adding a row |
| Inserting inside a merge's span | As adding a row (column) | That merge's entry, grown |
| Deleting a row (column) a merge spans | As today | The entry of each merge it changes or removes |
| Clearing several cells | Those cells' texts | — |

### The room's check

Merges add no check step. In the order of checks (**Links in text**): a malformed `mergeMap` is `invalid_update` at
step 1 (`readBoard`); document v24's merge rules are `invalid_document` at step 4 (`validate`). `repair` does not
change tables: the room never repairs, shrinks or drops a merge. A refused update takes the existing refused-edit path
in `packages/board-sync/src/session.ts` (the session drops with `refused_edit`, rejoins and reads the room's board), as
every refused edit does.

### Concurrent changes

**Arrival order.** The room's `promote()` (`packages/board-room/src/conflicts.ts`) is extended to assignments of a
`mergeMap` key. It re-assigns such a write only when the whole chain is live: the `mergeMap` is the live value of the
key `mergeMap` of an object map that is the live value of its id in `objects`, and that object's `type` is `"table"`.
A write into a `mergeMap` that is no longer live, or of a deleted table, is skipped. Deleting a `mergeMap` key is not
promoted, as no deletion is. So of two concurrent writes of the same anchor's merge, the one the room accepts last
is kept.

**Merges are counted in the current order.** A merge stores only its anchor and its counts, so a concurrent change by
someone who had not seen it (an insert, duplicate, move or delete on that axis) may change which rows or columns it
covers. The room accepts the merged result whenever document v24's merge rules hold for it, and otherwise refuses the
update that arrives second (`invalid_document`); nothing is repaired. Changes then merge like this, in addition to
sync v15's cases:
- **two merges that do not overlap:** both kept;
- **two merges that overlap** (different anchors): the later arrival is refused;
- **two writes of the same anchor's merge** (two merges, or a merge and a change of it, with the same anchor key):
  by the arrival order above, the later arrival's `{ rows, columns }` is kept. The texts the earlier one emptied stay
  empty, also in cells the kept value no longer covers. Refused when the kept value then overlaps another merge or
  covers a cell with text;
- **a write and a delete of the same anchor's merge** (a merge or change of it, and a split, or a merge that replaces
  it under another anchor): the write is kept whatever the order, since a delete removes only the value its author had
  seen and is not promoted. With a split, the result is the written merge and is accepted when the rules hold. With a
  replacing merge under another anchor, the kept entry's anchor lies inside the replacing merge, so the two overlap
  and the later arrival is refused;
- **two merges that replace the same merge under different anchors:** each deletes the old entry and sets its own;
  both contain the old merge's cells, so they overlap and the later arrival is refused;
- **a merge and typing in a cell it covers:** the merge empties the text it had received; letters it had not received
  survive the merge of the two texts, so the result holds a covered cell with text and the later arrival is refused.
  Typing in the anchor cell is kept;
- **a merge and an insert, duplicate or move across its span:** an empty row (column) that comes into the span is
  covered and the span's last row (column) leaves it, holding the empty texts the merge left: accepted. Refused when a
  row (column) with text in the span's columns (rows) comes into it, when the span would run past the table's end, or
  when the merge would then overlap another merge;
- **a merge and a delete of a row or column in its span:** refused when the deleted row (column) held the anchor;
  otherwise the span counts on into the next row (column): accepted only when that one holds no text in the span and
  the span stays inside the table;
- **a split and typing in the merged cell:** both kept;
- **moves:** different rows (columns) moved at once are kept (subject to the rule just below); the same row moved by two people takes the order
  key the room accepts last; two moved into the same gap may get equal keys and are read in id order. A move and a
  delete of the same row: the delete wins (sync v15). A move by someone who had not seen a merge is accepted or
  refused by the merge rule above, never repaired;
- **inserts, duplicates and moves at once:** kept, order keys deciding, as sync v15's concurrent adds, **only when the
  merged result passes every document rule**: the merge rules and the limits (at most 50 rows and 20 columns a table,
  and document v24's board-wide limits). Two inserts or duplicates each valid alone that together pass a limit, or
  that bring a row with text under a merge, are refused for the later arrival.

The client whose update is refused reloads the room's board through the existing refused-save recovery.

### The client keeps its last valid board

A client applies an accepted remote update (`update` frame) to a document that may still hold its own edits the room
has not yet answered (`packages/board-sync/src/session.ts`, the `update` and `saved` branch), and replays waiting
edits after a `joined` frame. The merge of the two can break document v24's rules (for example two overlapping
merges) although each was valid alone. The room either refuses this client's pending edit or, when a later accepted
update (for example a split of the conflicting merge) makes it valid again, accepts it; its answer comes later. Until
the board is valid again the client never shows or builds on it:
- **`capture()` never emits it.** `capture(doc)` in `packages/board-sync/src/undo.ts` checks the board it reads with
  document v24's `validate` and throws `Error("invalid_document")` instead of returning a state whose board fails it
  (as it already throws when the codec refuses the map).
- **The session holds.** `BoardSession` keeps the last board read from its document that passed `validate`. When,
  after applying any update, its board fails `validate` (or the codec throws), the session is **held**: its `board`
  getter returns that last valid board, the update is not observed by its history (no `observe` with a failing
  state), and `change` and the change report are not raised for it. The session keeps the **last valid state**
  (`capture` taken before that update). While held, each later `update` or `saved` frame is applied to the document
  and the board is checked again. While held, `edit`, `undo` and `redo` send nothing and answer
  `join_required` (the existing `blocked()` answer), so no edit or undo step is built on a board that fails the rules.
- **A valid board releases the hold.** When, after a frame applied while held (a remote `update`, or the `saved`
  receipt of this client's pending edit), the board passes `validate` again, the session captures again and
  **reconciles its history**: it calls `history.observe(last valid state, new state, false)`, so every entry whose
  unit changed during the hold is treated as changed by someone else (as for any remote update), then releases the
  hold: the `board` getter returns the board as read, `change` is set from that frame (`remote` with its
  `connection`, or `own` for `saved`), and the change is reported once. If that capture or reconciliation throws, the
  session drops with `refused_edit` and rejoins instead.
- **Or the hold ends with the reload.** The room's refusal of the pending edit takes the existing path (drop with
  `refused_edit`, rejoin); the `joined` frame replaces the document with a fresh one, the history is cleared as on
  every rejoin, and the hold ends with the room's board as the last valid one. If the session is held with no
  outstanding request (which the room's checks exclude), it drops with `refused_edit` and rejoins at once.

So the web client keeps showing its last valid board, and its table selection and editor are not recomputed from a
board that fails the rules, until a valid board, or the refusal and reload, resolve it.

### Undo on hosted boards

`capture` in `packages/board-sync/src/undo.ts` no longer takes a table's `mergeMap` as one value. For a table it adds
one unit per live `mergeMap` entry: key `merge:<row id>:<column id>`, value a copy of `{ rows, columns }`, identity
the item identity of that key's assignment, exactly as `place` and `tableStyle` are guarded today. `stepBetween`'s
table rule (keys of both states) records a merge added (`before` absent), removed (`after` absent) or changed, and a
table step still touches exactly one table.

`restoreTable` applies a step in this order: the axis entries as today; then it removes **every merge the step
touched** (every merge named by one of its `merge:` entries, whatever its restored value, so a merge whose anchor is
kept but whose span changed is removed too); then the cell texts; then it sets each touched merge whose restored
value is present to that value; then the result is validated **once**. So no cell text is restored while a merge the
step changed still covers it. **Every text the step restores must be restored:** when a cell the step gives a
non-empty text is covered by a merge the step does not touch (a merge someone else made since), `restoreTable`
answers no result, and the **whole** inverse is refused with today's hosted refusal words
(`changed_by_others`: `Someone else changed that, so it was not undone.`, for Redo the existing Redo words); no part
of it is applied and no text is skipped silently. Sync v15's rules
stand: the step is applied only if the table exists and every guarded value is unchanged since the step, otherwise
nothing of it is applied; the whole result is then checked by `validate`, and `undo_invalid` shows the same words as
`changed_by_others` (`Someone else changed that, so it was not undone.`; for Redo, the existing Redo words).

Each of these is **one** step of its author's history (one `edit`, one `record`; a drag is recorded once, on release),
and its Undo and Redo are one step too:
- **Undo of a merge** deletes its entry, sets back the merges it replaced, and puts back **every text it emptied**, in
  one update. Redo empties them and sets the entry again. A merge that grows a merge under the same anchor (one
  `merge:` entry changed from the smaller value to the larger) is undone by removing the entry, restoring the texts
  the larger span emptied and setting the smaller value; Redo removes it, empties those texts and sets the larger.
- **Undo of a split** sets the entry again. If a cell it would cover has since received text, or the merge would now
  overlap another or run past the table, the result fails `validate` and nothing is applied (`undo_invalid`).
- **Undo of a move** gives the moved ids back their recorded order keys (the hint's `orders`, as for a restored row).
- **Undo of a duplicate** deletes the copies, their texts and their copied merges' entries.
- **Undo of an insert inside a span** deletes the row (column) and sets the merge back to its recorded value.
- **Undo of a delete** restores the row (column), its texts and every merge entry the delete changed or removed.
- **Undo of clearing several cells** puts back every cleared text.

A remote write of a merge entry kills this connection's entries for that key, as any remote write kills the entries
for the units it assigned.

### A remote merge over the cell being edited

A client learns of it from the update itself; nothing is added to the room. After an `update` frame,
`BoardSession.change` is `{ origin: "remote", connection }` (`packages/board-sync/src/session.ts`), and the web
client's table change callback (`onTableChange` in `apps/web/src/state/use-hosted-board.ts`) passes the table as
received, the selection, whether a cell is being edited, the origin and the label to `validTableSelection` in
`apps/web/src/table.ts`. The **label** is the one the remote row-delete notice uses: the `label` of the presence in
`hosted.presence.others` whose `connection` is the change's `connection`, or `Someone` when there is none.

`validTableSelection` gains one case, checked after the existing missing row and column case, and it is given the
table **before** the update as well (the callback already holds it): when a cell is being edited and, in the table as
received, that cell is a **covered** cell (it lies in a merge not anchored at it), the result's selection is the
**merged cell** (a single-cell selection of the merge's anchor), and the editor closes. The notice

`<label> merged cells you were editing.`

shows only when the origin is `remote` **and the update added or changed the `mergeMap` entry that now covers the
cell**: the table before the update has no merge with that anchor and the same `{ rows, columns }`. When that merge
was already there unchanged and an accepted move, insert, duplicate or delete alone brought the edited cell under it
(merges count in the current order), the editor closes and the merged cell is selected with **no notice**, so nobody
is named for a merge they did not make.

The callback then takes its existing branch for a changed selection: the editor closes (composition ended, the text
session finished), the merged cell is chosen, and the notice, when there is one, shows through the existing notice
path (`tables.setMessage`). Closing writes nothing for the covered cell. When the edited cell is the new merge's
anchor, or is still not covered after a remote move, insert, duplicate or split, nothing closes and no notice shows:
ids are stable, so the edited cell's address is unchanged, and the editor follows the cell's live text as today. What a selected cell that is not being edited becomes when it is covered is
[interaction v54](0001-interaction-v54.md)'s rule.

### Roles, presence, comments and votes

Owners and editors write merges, moves, duplicates and inserts as above; a viewer's edit is refused as every
viewer's edit is today. No frame or presence key changes: a selection of cells, rows or columns is published as the
whole table, as today, so others see the existing outline round the table. A merged cell is not a comment anchor or
vote target of its own; the table stays one object for both.
