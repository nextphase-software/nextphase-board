# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v15 (2026-11-17)

Status: Draft for 0011-W1 v1. Replaces [sync v14](0003-sync-v14.md), whose rules remain in force word for
word except as below. [Document v20](0001-document-v20.md) adds the **table** object type and schema
version 14. This version says how a table lives in the room's shared document, so that several people can
edit one table at the same time without losing each other's changes, and how hosted Undo and the room's
arrival-order rule treat it.

## Schema version 14 in the room

A room's **live** board is always version 14. Every rule sync v14 gives for version 13 (pages in
`pageMap`, the object map's `page` key) applies to version 14.

**What the codec accepts** depends on what it reads; version and page layout are checked separately:

| Reading | Accepted |
| --- | --- |
| A client update, and the live board after any edit | Version 14 with `pageMap` |
| A stored storage-8 snapshot or a storage-8 backup's snapshot and replayed head (load and backup verification) | Version 13 or 14 with `pageMap` |
| A stored storage-7 snapshot or backup (load, restore, backup verification) | Version 10–13 with a live `pages` value (the existing legacy reading), or 10–12 as today |

Backup verification checks the retained bytes as stored, before any upgrade, then upgrades the head.

**Stored rooms upgrade when they load,** in one shared-document transaction, by the room's storage version
and stored schema version:

| Stored room | Upgrade |
| --- | --- |
| Storage 7 or 8, schema 10–12 | The existing `upgradeStored` to 13, then the schema-only step below |
| Storage 7, schema 13 (a live `pages` value) | Sync v14's `pageMap` conversion (object `page` values unchanged), then the schema-only step |
| Storage 8, schema 13 (`pageMap`) | The **schema-only step**: the board map's `schemaVersion` becomes 14. No other key is written; object `page` values are never rewritten |

The upgrade is not a person's edit: no edits row, receipt, revision or history version; the room writes the
snapshot at the **unchanged** current revision. The room's transition check keeps a board's version fixed
within an edit, so a client edit never changes the version.

**History.** The automatic capture rule compares the live board with the latest captured version after
normalizing both as `upgrade` does; a version 13 capture and its version 14 upgrade with no other change are
therefore equal and cause no new capture (history.ts's legacy comparison gains version 13, keeping `pages`
and every object's `page`).

**Reading other inputs.** A created or imported board, a restored history version and a backup are first
validated **at their declared version** (so a version 13 document holding a table is refused
`invalid_document`), then upgraded to 14 by document v20's `upgrade` before they are persisted or served.
Versions 10–12 keep today's rules (import and create still refuse them; history, restore and backups still
read them). Team templates keep their format (an object list with no version): their objects are validated
inside a version 14 wrapper, with today's template limits.

## A table's object map

A table's object map holds exactly these **live** keys:

| Key | Value |
| --- | --- |
| `generation`, `type`, `page`, `order`, `group`, `section` | As for every object (sync v14); `type` is `"table"` |
| `place` | A plain value `{x, y}` (document v20) |
| `tableStyle` | A plain value `{textSize}` |
| `columnMap` | A shared map keyed by column id. Each live entry is a shared map with exactly the live keys `order` (an order key, sync v14 "Order keys") and `width` |
| `rowMap` | A shared map keyed by row id. Each live entry is a shared map with exactly `order` and `height` |
| `cells` | A shared map keyed by **cell key** `<row id>:<column id>`. Each live value is a shared text with no formatting attributes |

A table has no `geometry`, `text`, `style`, `marks`, `ends` or `connectorStyle` key. Its width and height
are not stored in the shared document; reading computes them as document v20's sums. The codec reads a
table through its own branch, **before** the generic rectangle handling, and requires `place` to be a plain
value with exactly `x` and `y` and `tableStyle` with exactly `textSize` (missing or extra keys are
`invalid_update`, as are non-integer coordinates or an unknown text size).

### Reading

**Live and deleted keys.** Yjs keeps deleted map entries as tombstones. The codec checks presence, shape and
count on **live** keys only, and tolerates a deleted key only where its name is one this map may hold (an
id for `columnMap` and `rowMap`, a cell key for `cells`, a listed key for the object and entry maps).
It refuses with the existing `invalid_update` reason:
- a missing live key, or any live key not listed above;
- a live `columnMap` or `rowMap` key that is not a lowercase UUID, or an entry that is not a shared map with
  exactly its two live keys, a valid order key and an integer size;
- a live `cells` key that is not two lowercase UUIDs joined by `:`, or a value that is not a shared text
  without attributes;
- a deleted key of a name this map may not hold.

Columns are the live `columnMap` entries sorted by `order`, ties broken by id (code unit), as pages are;
rows likewise from `rowMap`. The document's `cells` holds one entry `{row, column, text}` for each live
`cells` value whose row id is a live `rowMap` key, whose column id is a live `columnMap` key and whose text
is not empty, in row order then column order. A live `cells` value whose row or column is not live (an
**orphan**) is not read and is not an error. Document v20's rules then apply to the board as read.

### Writing

The adapter's `set` receives the next whole board and, from a table step, the **table order hint**: the
table id, the axis (`column` or `row`) and the moved ids (an added row or column is moved; a dragged or
restored one too; other steps give none). It travels through the same commit seam as v14's moved pages
(`use-board-document.ts` to `session.ts` to the adapter), typed, and through hosted Undo and Redo; the
`update` frame does not change. For each table, inside the one transaction (initialization and cleanup apply to **every table the commit
writes at all**, that is every table whose next value differs from its stored one):
1. `place` and `tableStyle` are written only where the value differs.
2. `columnMap` and `rowMap` each follow sync v14's `pageMap` writing rule on their own: delete entries no
   longer in the table; add an entry for each new id; write a size only where it differs; write order keys
   by v14's steps 4–7 with the hint's moved ids for that axis. A rebalance renumbers only that axis of that
   table.
3. `cells`:
   - **Initialization.** Every live (row, column) pair of the next table that has no live text gets a new
     empty shared text, so adding a row creates one text per column and adding a column one per row, in the
     same transaction as the entry.
   - **Edits.** For each cell whose next text differs from its stored text, the stored text is changed by the
     grapheme-diff rule sticky text uses (one delete and one insert at the changed span only). A cell
     emptied by an edit keeps its (now empty) text; texts are never deleted for being empty.
   - **Cleanup.** Every live `cells` value whose row or column is not in the next table is deleted: the
     cells of a deleted row or column, and any orphans.

**Net writes.** A step's update is limited to its own writes plus the writes the rules above require of
it:

| Step | Its own writes | Also required |
| --- | --- | --- |
| Typing in a cell | That cell's text | The row's `height` when the same step raises it (interaction v45) |
| Adding a row (column) | One `rowMap` (`columnMap`) entry and one empty text per column (row) | Order keys of other entries only when v14's steps 5–7 require (for example ties) |
| Resizing a row or column | One `height` or `width` | — |
| Restoring a deleted row or column (Undo) | The entry with its order key and size, and its cells | v14's steps 5–7 |
| Deleting a row (column) | The entry and its cells | — |
| Any step | — | Initialization of missing intersections and cleanup of orphans in that table |

### Concurrent changes

The room's arrival-order rule (`promote()`) is extended to the `order`, `width` and `height` writes inside
`columnMap` and `rowMap` entries. It re-assigns such a write only when the whole chain is live: the entry is
not deleted, its parent map is the live value of the key `columnMap` (or `rowMap`) of an object map that is
the live value of its id in `objects`, and that object's `type` is `"table"`. A write into a deleted entry,
an axis map that is no longer live, or a deleted table is skipped, as v14 skips writes into deleted page
entries. Adding or deleting an entry, and creating, editing or deleting cell texts, are not promoted.

Changes then merge like this:
- **different cells:** both kept;
- **the same cell, its text already existing:** both people's insertions and deletions are kept, merged
  letter by letter, as for sticky text;
- **the same cell, its text created by both at once** (only possible at the intersection of a row and a
  column added concurrently by two people, before any later write initialized it): Yjs keeps one of the two
  new texts, the same on every replica; the other person's first typing there is lost. Any later write by
  anyone initializes intersections, so the window is that one race;
- **rows or columns added at once:** all kept; two added between the same neighbours may get equal keys, and
  reading orders them by id. The intersection of a concurrently added row and column is initialized by the
  next write;
- **the same column's width, or row's height, or one's order key:** the later arrival wins;
- **a delete of a row or column and an edit inside it** (typing in its cells, a resize or a move): the delete
  wins. Text typed into an existing cell of it is a write into a deleted text and is lost; a text created
  in it after the delete is an orphan, not read, and deleted by the next write of that table by anyone. The
  edit carrying it is still accepted;
- **a delete of the whole table and any edit inside it:** sync v14's object rule, unchanged.

An edit whose result, as read, breaks document v20 (for example the last two rows deleted by two people at
once, a 51st row, or a cell over 1,000 code points after a merge) is refused with the existing
`invalid_document` reason, and the client's existing refused-save recovery reloads the room's board.

## Undo on hosted boards

Whole-object units are unchanged: placing, duplicating or deleting a whole table is an object unit, and
undoing a deleted table re-creates it with a **fresh table id and generation** as every deleted object is
re-created today; its column, row and cell ids, sizes and texts are kept (they are unique only within the
table) and its order keys are a fresh rebalance of its display order on each axis.

**What every hosted Undo guarantees.** The guard is checked by the issuing tab against what it has received.
A change by someone else that is still on its way to the room when the Undo is sent may be overwritten by the
Undo, which arrives later (the room's arrival order). This is true of every hosted Undo today and is not
changed here.

Every other table step (interaction v45 "Undo") is one **table step** of its author's history. A table step
touches exactly one table and nothing else. `undo.ts` records, at the step, an immutable snapshot of each
thing it touched, before and after:
- each touched `columnMap` or `rowMap` entry: present or absent; when present, its `order` and size and the
  item identities of those two values;
- each touched cell: present or absent; when present, its text and its text identity;
- `place` and `tableStyle` when touched: value and item identity;
- the table's object identity.

**The guard** for Undo is the after-snapshot (for Redo, the before-snapshot): the step applies only if, for
every recorded thing, the live state matches it — a present thing has the same identities, an absent entry
is still absent. One exception: a live **orphan** text at a cell key the Undo restores (typed into the deleted
row or column by someone else) does not break the guard; it is deleted and replaced by the restored text.

**Undo and Redo are atomic.** A table step is undone (or redone) only if the table still exists and every
guarded value is unchanged since the step (or since its Undo). Otherwise **nothing** of it is applied, and
the existing words `Someone else changed that, so it was not undone.` show (for Redo, the existing Redo
words). In particular:
- **Undo of an add** deletes the added entry and its cells; refused if someone has since typed in one of its
  cells, resized or moved it.
- **Undo of a delete** adds the entry back with its id, order key and size, and its cells with their keys and
  texts. Any orphan text at one of those keys is first deleted and replaced. Refused if a column (row) that
  one of the restored cells belongs to has since been deleted, or the id has since been added again.
- **Undo of a resize, a text size change, Delete content or a cell's editing session** restores the values
  the step changed.
- **Redo** applies the step's after-values under the same rule.

## The room

`history.ts` and every room check that accepts schema version 13 accepts **13 and 14** on reading and holds
**14** live: `room.ts` creates new boards at 14, its version check after `validate` expects 14, and the load
path upgrades as above; `edits.ts` expects 14 after an edit. The room's storage version stays **8**
([hosted storage v12](0003-hosted-storage-v12.md) unchanged). Images are still refused as today.

## Presence, comments and votes

No frame changes. A table is one object for presence selections, comment anchors (attached to the table,
not to a cell, named `Table` by the existing rule for an object without text) and vote targets (`voting:
true`); [interaction v45](0001-interaction-v45.md) says what each shows.
