# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v6 (2026-11-03)

Status: Draft for 0005-W1 v1. When accepted it replaces [sync v5](0003-sync-v5.md) for later
work. Every rule, message, limit and close code of v5 (and through it v4) still applies, word for
word, except where this version changes it. It adds **comments** on the room connection: the
`comment` message, its answers, the snapshot of the board's threads after `joined`, and the
changes the room sends to everyone ("Comments"). Edits, `joined`, recovery, the progress deadline
and the close codes are v5's.

What a thread and a comment are, how they are anchored, who may do what, the order, the limits
and the refusal order are in the [comments contract](0005-comments-v1.md). The room's storage is
in [hosted persistence v4](0003-hosted-persistence-v4.md); who may do what is in
[access v5](0003-access-v5.md); what the web app shows is in
[hosted storage v5](0003-hosted-storage-v5.md).

## Framing

v5's table applies, with these rows added:

| Direction | `kind` | Fields |
| --- | --- | --- |
| client → room | `comment` | `epoch`, `requestId` (1–100 characters), `operation` ("Comments") |
| room → client | `comment_saved` | `requestId`, `sequence` |
| room → client | `comment_refused` | `requestId` (when the message had a readable one), `reason` |
| room → client | `comments_snapshot` | `reset: true` and `sequence` (the board's last comment sequence, 0 when none), or `done: true` |
| room → clients | `comment_changed` | `threadId`, `thread`, and as the change needs `sequence`, `by`, `commentId`, `comment` ("Comments") |

A comment message never changes the board's `revision` and never produces `received`, `saved` or
`update`, nor `refused` apart from v4's size refusal ("Size"); an edit never produces a comment
answer. A `comment_refused` is not a
`refused`: v4's rejoin after a refusal ("The shared client", "A refused edit") never follows it.

## Comments

**The operation.** `operation` is a JSON object with an `action` and the fields the action needs.
IDs are lower-case UUIDs; `text` is a string ([comments contract](0005-comments-v1.md), "Text");
`anchor` is `{ "objectId", "u", "v", "x", "y" }` (comments contract, "Anchors"). Other fields of an
operation or an anchor are ignored and never stored.

| `action` | Fields |
| --- | --- |
| `start` | `threadId`, `commentId`, `anchor`, `text` |
| `reply` | `threadId`, `commentId`, `text` |
| `edit` | `threadId`, `commentId`, `text` |
| `delete_comment` | `threadId`, `commentId` |
| `delete_thread`, `resolve`, `reopen` | `threadId` |
| `move` | `threadId`, `anchor` |

**Handling.** The room handles a `comment` message in its one order of messages, before and apart
from the edit path: a viewer's comment is checked by the comments contract's rules, and a viewer's
`edit` is still refused with `role_too_low` exactly as in v4. The room checks the message as the
comments contract's "Checking an action" says. A refused action is answered `comment_refused` to
the sender only, with the reason, and nothing is stored. A saved action is stored with its receipt
in one storage transaction; then the room sends `comment_changed` to **every** connection of the
board, the sender's included, and then `comment_saved` to the sender. No connection sees a comment
action before it is stored.

**What `comment_changed` carries.** `thread` is the thread's whole current record without its
comments (the comments contract's thread fields), or `null` when the thread is gone. `comment`
is one comment's whole record, or `null` when that comment is gone. `by` is the label of the
person whose saved comment action this is, from their connection ([identity v3](0003-identity-v3.md),
"Labels"); it is sent with every frame that has a `sequence`.

| Saved action | `comment_changed` |
| --- | --- |
| `start` | `sequence`, `by`, `threadId`, `thread`, `commentId`, `comment` (the first comment) |
| `reply`, `edit` | `sequence`, `by`, `threadId`, `thread`, `commentId`, `comment` |
| `delete_comment` of a reply | `sequence`, `by`, `threadId`, `thread`, `commentId`, `comment: null` |
| `delete_comment` of the first comment, and `delete_thread` | `sequence`, `by`, `threadId`, `thread: null` |
| `resolve`, `reopen`, `move` | `sequence`, `by`, `threadId`, `thread` |
| A saved edit that detached a thread (comments contract, "Detaching") | `threadId`, `thread` (no `sequence`: it is not a comment action) |

A thread that is gone takes all its comments with it; no frame is sent for each. The detaching
frames are sent after the edit's `saved` and `update`, one per detached thread. A saved edit that
only moves or resizes an attached thread's object sends no comment frame: clients draw attached
pins from their own board.

**The snapshot.** Right after `joined`, before anything else on that connection, the room sends
the board's comments to the joining connection:

1. `{ "kind": "comments_snapshot", "reset": true, "sequence": <last comment sequence> }`;
2. one `comment_changed` with `threadId` and `thread` (and no `sequence`) per thread, open and
   resolved, in thread `sequence` order;
3. one `comment_changed` with `threadId`, `commentId` and `comment` (and no `sequence`) per
   comment, in comment `sequence` order;
4. `{ "kind": "comments_snapshot", "done": true }`.

Each frame holds one row, so no frame is near the transport's limits however many threads a board
has. A person with no role never gets a `joined`, and so never any thread.

**Retrying a comment.** A comment's receipt is matched by the SHA-256 of the UTF-8 text
`comment:` followed by the operation as `JSON.stringify` writes the object the room parsed (its
keys in the order the message had them). If the same person sends the same request ID with the
same operation again, the room answers `comment_saved` with the stored `sequence`, then sends that
connection a fresh snapshot (steps 1 to 4), and changes nothing. The same request ID with a
different operation, or a request ID the person used for an edit, is refused with
`request_id_reused`; an `edit` with a request ID the person used for a comment is refused with
`request_id_reused` too ([hosted persistence v4](0003-hosted-persistence-v4.md), "One database
per board", `receipts`). The receipt is checked after access (the comments contract's step 2),
so a retry under an old epoch is refused with `epoch_changed`.

**Reasons.** `comment_refused` carries one of `bad_message`, `no_access`, `epoch_changed`,
`request_id_reused`, `empty_text`, `too_long`, `identifier_reused`, `thread_deleted`,
`comment_deleted`, `not_author`, `bad_anchor`, `anchor_deleted`, `comment_limit` and
`rate_limited`. v4's message size refusal (`message_too_large`) and close codes apply to `comment`
messages as to any other.

## The shared client

v5's section applies, with these additions. Nothing in it about edits, requests, recovery or undo
changes for comments.

- **Threads.** The session keeps the board's threads, each with its comments in `sequence` order,
  in the open tab's memory only. Every `joined` clears them and sets `commentsReady` to false; a
  `comments_snapshot` with `reset` clears them again and sets `commentsReady` to false (also the
  `reset` a retry answer sends); the `done` frame sets `commentsReady` to true. A `comment_changed` with `thread: null` deletes the thread and its comments; with a
  `thread` it replaces the thread's record and keeps its comments; with `comment: null` it deletes
  that comment; with a `comment` it adds or replaces it. The session reports every comment frame to
  its caller.
- **Sending.** `comment(operation)` sends a `comment` message and returns its new request ID (a
  random lower-case UUID). It refuses, without sending, with `join_required` while the session is
  not joined or `commentsReady` is false. It serializes the message once and keeps that text, with
  the epoch and restore generation it was sent under. It does not wait for recovery
  (v5, "Recovering after an interruption"): a comment may be sent and saved before edits that are
  still waiting or being sent again, which keep their own order among themselves; a comment never
  holds an edit back.
- **Comment requests.** Each is `sent`, `saved`, `refused` or `unconfirmed`. `comment_saved`
  makes it `saved`; `comment_refused` makes it `refused` with the reason. A request `saved` or
  `refused` never changes again. A comment request has v5's ten-second progress deadline ("The
  progress deadline"), which ends the attempt as for an edit. When an attempt ends for any reason,
  every `sent` comment request becomes `unconfirmed` (reason `connection_lost`).
- **No queue.** The session never sends a comment again by itself: not on a rejoin, not after
  recovery. `retryComment(requestId)` sends an `unconfirmed` request again, as the same message
  text, only while joined with `commentsReady` true and only when the epoch and restore generation
  are the ones it was first sent under; it then becomes `sent` with a new deadline. Otherwise it
  sends nothing and returns the first of these that applies: `join_required` (not joined, or the
  snapshot not done), `not_retryable` (no such request, or it is not `unconfirmed`), then
  `access_changed` (the epoch or restore generation differs). `discard()` and `close()` send nothing for comments.

## Size

v4's limit applies to `comment` messages: one over 1 MiB is refused as v4 says, with a `refused`
`message_too_large` that has no `requestId`, before the room reads it, and the shared client
handles that `refused` as v4 says (it rejoins). The shared client never sends such a message: it
refuses, without sending, text that is empty (`empty_text`) or longer than 4,000 code points
(`too_long`), so a comment it sends is at most about 16 KB. A comment frame from the room holds one
thread or one comment and is far below 1 MiB.

## Not in this version

v5's list, and: queuing or resending comments by the client itself; comment frames before
`joined`; paging or partial snapshots; live movement of another person's pin while they drag.
