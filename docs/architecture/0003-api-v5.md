# 0003 — Server API contract

CONTRACT VERSION: 0003 API v5 (2026-11-04)

Status: Draft for 0006-W1 v1. When accepted it replaces [API v4](0003-api-v4.md) for later work.
Every route, rule and refusal of v4 still applies, word for word, except where this version
changes it. It changes one route: **`POST /workspaces/:workspace/boards` may carry a board
document**, so that a board file becomes a new board in one request ("Creating a board from a
document"), and that route alone accepts a request body of up to 13 MiB. Who may call each route
is in the [access contract](0003-access-v5.md); token checks are in the
[identity contract](0003-identity-v3.md); the room connection is in the
[sync contract](0003-sync-v6.md); how a room starts from a document, and how one is discarded, is
in [hosted persistence v5](0003-hosted-persistence-v5.md); the document itself is
[document v11](0001-document-v11.md).

## Common rules

v4's rules apply, with the body limit replaced: a request body over 1 MiB (1,048,576 bytes) is
refused with 413 `body_too_large`, except on two routes, each with the same refusal above its own
limit:

| Route | Limit |
| --- | --- |
| `POST /operator/boards/:board/restore` | 16 MiB (16,777,216 bytes), as in v4 |
| `POST /workspaces/:workspace/boards` | 13 MiB (13,631,488 bytes) |

The creation route's limit is larger so that a document at the 2 MiB limit fits however its
client writes the JSON (an escaped character can take six bytes); it applies to every creation
request, with or without a document. Every other route keeps the 1 MiB limit.

## Routes

v4's table applies, with this row in place of v4's:

| Method and path | Body | Success |
| --- | --- | --- |
| `POST /workspaces/:workspace/boards` | `{}`, `{ "title": string }`, or `{ "title": string, "document": object }` (see "Boards" and "Creating a board from a document") | 201 `{ "id", "workspaceId", "title", "createdAt" }` |

## Boards

v4's section applies, with these changes. The creation body is a JSON object that is exactly one
of: empty, giving the title `Untitled`; `{ "title" }`; or `{ "title", "document" }`. A missing
body, any other set of keys (`{ "document" }` without `title` included) or a body that is not an
object is 400 `bad_request`. The title rule is v4's (1 to 120 code points, not only white space,
no unpaired surrogate, no U+0000), for both shapes.

Creating a board **without** a document is unchanged: the server writes its row in Supabase,
then answers, and the room is created empty the first time a request loads the board. v4 lists
those requests as "a join ticket, a join or an export"; this version corrects the list: a join
ticket, an export, a rename or an operator backup. A join never creates a room: on a room that is
not created it answers 401 `ticket_invalid`, as it does today ([hosted persistence
v5](0003-hosted-persistence-v5.md), "How a room is created").

## Creating a board from a document

`POST /workspaces/:workspace/boards` with `{ "title", "document" }` creates a new board in the
workspace whose room holds that document from the start. `document` is a board document as a JSON
object (not a string holding JSON).

**Checks, in this order.** Each refusal is answered before anything is written: no row, no room,
no Supabase call beyond the access check.

1. The token (v4, "Common rules").
2. The workspace ID: not a lower-case UUID is 404 `not_found`.
3. Access, as for any creation (access contract, "Create a board in the workspace"): a person
   with no role in the workspace gets 404 `not_found`; a workspace viewer or guest (a guest's
   board grant does not count, even an editor grant) gets 403 `role_too_low` with
   `"needed": "editor"`.
4. The body: over 13 MiB is 413 `body_too_large`; not JSON, not an object, or an object whose keys
   are not exactly one of the three sets above, is 400 `bad_request`.
5. The title rule: 400 `bad_request`.
6. The document: if it is not a valid board document of [document v11](0001-document-v11.md)
   (its `validate` rule; a `document` that is not an object, a string holding JSON included, is
   not), or its `schemaVersion` is not 10, the answer is 400 `invalid_document`.
   Older document versions are not accepted here; a client upgrades them first (the web app does,
   as Open board file does).
7. The size: if the document's canonical JSON (document v11) is over 2 MiB (2,097,152 bytes), or
   the canonical JSON of the document **as it will be stored** (below) is, the answer is
   400 `document_too_large`.
8. Pictures: if any object's `type` is `image`, the answer is 400 `images_not_supported`. Team
   boards hold no pictures in this version (no route stores a picture).

**What is stored.** The document as stored is the given document with `boardId` replaced by the
new board's ID and `title` replaced by the request's `title` (the request's title wins over the
document's own). Every other value is kept exactly: every object with its `id`, `generation`,
`order`, section and group membership, connector ends and every other field, and
`retiredGenerations`. The stored document's canonical JSON is therefore the given document's
canonical JSON with those two values changed. The file's own board ID is never used for anything.

**Steps.** After the checks pass:

1. The server writes the board's row in Supabase (the same call as a creation without a document,
   with the request's title). If that call fails or does not answer, nothing else is done and the
   answer is 503 `service_unavailable`, as for any creation.
2. The server asks the board's room to start from the document as stored (hosted persistence v5,
   "A room started from a document"). The room stores it at revision 0, in one storage
   transaction, before it answers.
3. The answer is 201 with the board's details, as for any creation. The board is listed in its
   workspace for everyone with a role there at once; it enters a person's Recents when they open
   it (v4, "Lists").

**When step 2 fails.** If the room refuses the document (409 `room_exists`: its storage was
already created, hosted persistence v5), fails, or does not answer, the server undoes the
creation: it deletes the board's row in Supabase and discards the board's room (hosted
persistence v5, "Discarding a room"). It attempts both, each even if the other fails. If both
succeed, the answer is the room's refusal (409 `room_exists`) or 503 `service_unavailable`, and
nothing of the board remains. If either fails, the answer is 503 `creation_cleanup_failed`.

**What "all or nothing" covers.** Every refusal, and every failure the server sees, leaves
nothing behind, except in two cases this version does not close:
- Supabase saves the row but its answer is lost: the server cannot know the new board's ID, so it
  answers 503 `service_unavailable` and the row stays, as a board with the request's title whose
  room is created empty the first time it is opened. A creation without a document has the same
  gap today (an empty `Untitled` board).
- The clean-up itself fails (503 `creation_cleanup_failed`): the board's row, its room (empty or
  holding the document, depending on where the creation failed) or both may stay; a row whose delete failed is listed as an ordinary board.

Closing these needs a board row that is hidden until its room is filled, which is a database
schema change and not part of this version.

**Retries.** There is no idempotency key: a request sent again, or the same document sent twice,
makes another board, each with its own ID and its own copy of the objects.

**Comments and access.** A board made from a document starts with no comments and no grants of
its own, as any new board: the request carries neither, and the document holds neither.
