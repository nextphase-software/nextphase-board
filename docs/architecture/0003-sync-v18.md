# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v18 (2026-11-25)

Status: Draft for 0012-W5 v1. Replaces [sync v17](0003-sync-v17.md), whose rules remain in force word for
word except as below; v17's text is kept here in full, with its version numbers moved on only where this version
requires it. [Document v22](0001-document-v22.md) adds the **link** object type (a **link card**: keys `url`,
`title`, `description`, `site`, `asset`, `layout`, `state`, `requestedAt`) and schema version **16**. This version
moves the room's live board to 16, lets a team board hold link cards whose thumbnail the room holds as a picture,
and makes a card's **arrival** (the one edit that fills in a pasted card) part of the paste's own Undo step. The
room's storage version stays **9** ([hosted storage v15](0003-hosted-storage-v15.md)); no frame, presence key,
socket message or service table is added.

v17 itself replaced [sync v16](0003-sync-v16.md) and added the **video** object type (keys `asset`, `poster`,
`pixelWidth`, `pixelHeight`, `durationMs`, `name`, `description`) and schema version 15; its rules for videos stay.

## Schema version 16 in the room

A room's **live** board is always version 16. Every rule sync v15 gives for version 14 (pages in `pageMap`, the
object map's `page` key, tables) applies to versions 15 and 16. Version 15 differs from 14 only in allowing video
objects, and version 16 from 15 only in allowing link cards. This section is the one place that says which schema
versions each input accepts; document v22 points here.

**Decoded type.** Because document v22 makes `BoardV14` and `BoardV15` aliases of `BoardV16`, `readBoard(doc, legacy?)`
in `packages/board-sync/src/codec.ts` claims neither. It returns the exported **`DecodedBoard`**: the union of
document v22's board shapes for versions 10 to 16, exactly as stored, unpaged for 10–12 (no `pages`, no object
`page`) and paged for 13–16 (`pages` and every object's `page`; version 15 built from `StoredItemV15`, version 16
being `BoardV16`). Its paged versions become 13, 14, 15 and 16. **`readLiveBoard(doc): BoardV16`** calls
`readBoard(doc)` and throws `Error("invalid_update")` unless the version is 16.

| Caller | Reads with | Allowed change |
| --- | --- | --- |
| `packages/board-sync/src/session.ts` (the `board` getter) | `readLiveBoard` | None at run time for reading (the returned type follows `readLiveBoard`); `edit` and `write` gain the arrival option below |
| `packages/board-sync/src/undo.ts` (the state reader) | `readLiveBoard` | None at run time (the returned type follows `readLiveBoard`); the arrival rule below |
| `packages/board-room/src/edits.ts` | `readBoard`, unchanged | Its schema check after `validate` expects **16** and stays in the `invalid_document` branch: a well-formed edit of another version is `invalid_document`, a malformed map `invalid_update`, as today |
| `packages/board-room/src/room.ts` load and `upgradeStored`; `history.ts` backup verification | `readBoard` | Narrow to `BoardV16` after upgrading |

**Input matrix.** Every input keeps exactly this range; each is validated at its declared version (so a version 14
document holding a video, or a version 15 document holding a link card, is `invalid_document`), then upgraded to 16
by document v22's `upgrade` before it is persisted or served:

| Input | Versions accepted, with their page layout |
| --- | --- |
| A client update, and the live board after any edit | 16, `pageMap` |
| A stored room at load, storage 7 (`readBoard(doc, true)`) | 10–12 unpaged, or 13 with a live `pages` value |
| A stored room at load, storage 8 or 9 | 10–12 unpaged, or 13–16 with `pageMap` |
| A history version's document (`documentBytes`: previews, restore, capture comparison) | 10–16 (JSON; 13–16 with `pages`) |
| A backup's snapshots and replayed head (`validateHistoryBackup`), storage 7 | 10–12 unpaged, or 13 with a live `pages` value |
| The same, storage 8 | 10–12 unpaged, or 13–14 with `pageMap` |
| The same, storage 9 | 10–12 unpaged, or 13–16 with `pageMap` |
| A created board (`room.ts`) and an imported board (`routes/boards.ts`) | 13–16 |
| Team template objects (`templates.ts`) | Validated inside a version 16 wrapper |

A backup head of storage 7 or 8 holds no image, no video and no link card ([hosted persistence v13](0003-hosted-persistence-v13.md); a link card needs
version 16, which storage 8 never holds).

**Stored rooms upgrade when they load,** in one shared-document transaction, whenever the stored version is not 16:

| Stored room | Upgrade |
| --- | --- |
| Schema 10–12 (any storage), or storage 7 with schema 13 | The existing steps (`upgradeStored`: pages, then `pageMap`), then the schema-only step |
| Storage 8 or 9, schema 13, 14 or 15 (`pageMap`) | The **schema-only step**: the board map's `schemaVersion` becomes 16. No other key is written |

The upgrade is not a person's edit: no edits row, receipt, revision or history version; the room writes the
snapshot at the unchanged current revision. `room.ts` creates new boards at 16 and its `upgradeStored` sets 16.
The transition check keeps a board's version fixed within an edit.

**History.** The automatic capture's legacy comparison (`history.ts`) gains version 15 (it compares 10 to 15), so a
version 15 capture and its version 16 upgrade with no other change cause no new capture.

## Editing

Step 5's clause from sync v16 ("every image object that the edit adds … `asset_missing`") is replaced by:

> and **every image object that the edit adds, or whose `asset` it changes, refers to an asset the room holds as a
> picture**, and **every video object that the edit adds, or whose `asset` or `poster` it changes, refers by
> `asset` to an asset the room holds as a video and by `poster` to an asset the room holds as a first frame, that
> is with the type `image/jpeg`** (hosted storage v14's held predicate), and **every link card that the edit adds
> with a non-null `asset`, or whose `asset` it changes to a non-null value, refers to an asset the room holds as a
> picture, of any picture type** (the same predicate as an image's). A poster held with any other picture type
> is refused. An image, video or link card whose id was on the board before the edit, as the same type with the
> same `asset` (and, for a video, the same `poster`), is not checked; a card whose `asset` is `null` is never
> checked. Otherwise the edit is `refused` with the reason **`asset_missing`**. Nothing is stored.

The check stays in `packages/board-room/src/edits.ts`, after every other step-5 check, and runs in the room's
ordered queue with every store's final step, clean-up and capture, so no asset can be stored or removed between
the check and the edit's write. A video upload's receiving part runs outside the queue but is invisible until its
final step (hosted storage v14), so it never changes this check's answer. The objects it walks are those that hold
an asset (`assetsOf(o).length > 0`, document v22), not only `isMedia` ones.

The same typed check is `requireHeldMedia(objects, typeOf)` in `packages/board-room/src/room.ts`, used by a staged
import's claim and create (hosted storage v15) and by team templates (`apps/server/src/templates.ts`): for a link
card with a non-null `asset` it requires `typeOf(asset)` to be a picture type, else 400 `asset_missing`; a card whose
`asset` is `null` passes.

So a board that holds a video whose video or first frame is missing, or a card whose thumbnail is missing, still
takes every other edit, rename, deletion of that object, Duplicate of other objects and Undo or Redo of other steps;
what is refused is adding such an object again, or changing its `asset` or `poster` to one the room does not hold
so.

A client sends an edit that adds a video only after its first frame's upload and then the video's upload to this
board answered 200 or 201 ([API v14](0003-api-v14.md)), or for a video copied (Paste, Duplicate) or restored
(Undo, Redo) on the same board, which uploads nothing ([interaction v50](0001-interaction-v50.md)). A client sends
the **arrival** edit that gives a card its `asset` only after the thumbnail's upload to this board
(`PUT /boards/:board/assets/:hash`) answered 200 or 201; a card copied (Paste, Duplicate) or restored (Undo, Redo)
on the same board uploads nothing ([interaction v52](0001-interaction-v52.md)). An `asset_missing` refusal takes
the existing refused-edit path in `packages/board-sync/src/session.ts` (the `refused` branch: the request is marked
refused, its deadline cancelled, the session drops with `refused_edit` and rejoins). For an arrival's request the
paster's browser then follows **One retry** (below), and nothing else.

## Link cards: paste, arrival and the 20,000 ms rule

A pasted card is written in **two edits**, both by the paster's browser:
1. **The paste** adds the card with `state: "loading"`, empty texts, `asset: null`, `layout: "vertical"`, the
   loading size and `requestedAt` (document v22). It is one ordinary Undo step.
2. **The arrival**, when the preview answer and the thumbnail's storage are done (interaction v52), changes only that
   card, and only its **finish keys**: `title`, `description`, `site`, `asset`, `state` (`"ready"` or `"linkOnly"`),
   `layout`, `width` and `height`. The paster's browser builds it from the card as its board holds it at the commit,
   so `x` and `y` are those it then holds (a move made while the card loaded is kept), changed only when the new size
   would cross the document bounds (shifted left and/or up just enough, interaction v52). No other key changes. The
   document adapter stores a rectangle as **one** shared value, `geometry` (`{ x, y, width, height }`), and the
   finish keys as their own keys; the adapter's single transaction writes `geometry` (when it differs) and every
   changed finish key together, so the arrival is **one update**. It is written only when interaction v52's gate
   passes (the same board opening, the active local writer or the live editable document, an owner or editor, and a
   card with the paste's `id`, `url` and `requestedAt` still on the board with `state: "loading"`); otherwise nothing
   is written (the card was deleted, undone, changed back to text or restored under a fresh `id`), and an uploaded
   thumbnail no object names is cleared by the existing clean-up of unreferenced pictures (hosted storage v15;
   [storage v5](0001-storage-v5.md) on single-user boards).

**Concurrent edits to a card.** Document v22 accepts any card size with any state, so the merge of an edit that
writes a card's `geometry` with an edit that writes its other keys is always a valid card. In particular, when another
person moves the card concurrently with its arrival (neither client had seen the other's edit), the two `geometry`
values conflict and the shared document keeps one of them (Yjs's rule for concurrent writes to one key), whichever
order the room receives them in. Both outcomes are **accepted** and neither is refused or repaired:
- the arrival's `geometry` is kept: the card is finished, at the place the paster's board held, and the move is lost;
- the move's `geometry` is kept: the card is finished at the moved place and keeps the loading size, 306 × 288 (a
  valid card size), and every client draws its face inside that rectangle (interaction v52).

The same holds for a move concurrent with a layout choice. A concurrent merge that breaks another document rule (for
example the state-and-keys table) is refused by the room's existing document check, as any invalid merge is today.

Viewing, copying, Duplicate, Undo, Redo, version restore, files and templates never send a preview request and never
write an arrival. A card whose arrival never comes stays `loading` in the document; every client draws and treats it
as link-only once its own clock is 20,000 ms or more past the card's `requestedAt` (document v22 link rule 5), and
nothing is written for that. Other people on the board see the loading card from the paste and the finished card
from the arrival, as ordinary remote edits.

## Undo, Redo and history

Hosted Undo and Redo restore video objects and link cards as they restore images: the step holds the object's
document keys, never file bytes, and no upload or preview request is made. A video and its first frame, and a
card's thumbnail, stay held while a version, the live board or a recent upload refers to them
([hosted persistence v13](0003-hosted-persistence-v13.md); the room's referenced set is `assetsOf` of every object,
so it includes cards' thumbnails); if one was removed, the step is refused with `asset_missing` through the path
above.

**The arrival amends the paste's step** (`packages/board-sync/src/undo.ts`). `SharedUndo` gains
`amend(before: State, after: State, id: string): boolean`, which the paster's session calls for the arrival edit in
place of `record`.

**How an edit is known as an arrival.** Each step below takes one new optional last parameter, `arrivalOf?: string`
(the card's `id`); without it every function behaves exactly as today. The web client's `commit(input, recordObject,
orderIds?, opens?, movedPages?, tableHint?, arrivalOf?)` (`apps/web/src/state/use-board-document.ts`) passes it
through `apply` to `HostedBoard.edit(board, group?, movedPages?, page?, tableHint?, arrivalOf?)`
(`apps/web/src/team/hosted-board.ts`), which passes it through its existing `deliberate` to
`BoardSession.edit(board, group?, movedPages?, page?, tableHint?, arrivalOf?)`, which passes it to `write`. `write`
captures `before`, sets the board as today, and then calls `this.history.amend(before, capture(this.doc), arrivalOf)`
instead of `this.history.record(…)`, and passes `arrivalOf` to `sendEdit(update, group?, touched?, arrivalOf?)`. An
arrival commit records nothing in the web client's own history and uses no edit group. Undo and Redo never pass
`arrivalOf`.

**The request carries it before dispatch.** The session's `Request` type gains `arrivalOf?: string`. `sendEdit` puts
`arrivalOf` on the request object **when it creates it, before it stores it in `requests`, before the size check and
before `sendRequest`**. So every refusal of that request is matched to the card, including the **synchronous** one:
`sendEdit` refuses a message above 1,048,576 bytes at once (it marks the request refused, drops with `refused_edit`,
rejoins and reports `{ kind: "refused", requestId, reason: "message_too_large" }`) before `edit` has returned. The
deadline, refusal and resend handling are otherwise exactly today's. `HostedBoard.changed`, for a `refused` event
whose `requestId` names a request with `arrivalOf` (read from `session.requests`), runs today's refusal branch
without the toast (`this.spotlight.clear(); this.clearPresence(); this.publish({ connected: false })`; no
`words.refusedEdit`) and notes the refused card id; every other event is unchanged. `HostedBoard.edit` keeps its
result exactly as today: `false` when not admitted (cannot edit, no session, or no change), otherwise `deliberate`'s
result (`true` once the session made a request, even one refused at once, or the session's reason string). A new
method `HostedBoard.arrivalRefused(id: string): boolean` answers `true` once for each noted card id (and forgets it),
else `false`.

**One retry.** This is the only rule for a refused arrival, on every path. When an arrival's edit is refused (matched
as above), the paster's browser makes **exactly one** further arrival for that card, the **link-only finish**,
silently: after the board has rejoined, when interaction v52's gate passes and its holds have cleared, if the card is
still on the board in `state: "loading"` with the same `id`, `url` and `requestedAt` and the 20,000 ms deadline
allows (a finish past it is the link-only finish anyway). It is committed as an arrival (`arrivalOf`), so it too is
part of the paste's step. If that retry is refused as well, or the card is no longer loading, nothing more is
written: the card stays `loading` and is drawn link-only once document v22's 20,000 ms have passed. No toast or
notice shows for either refusal.

**`amend(before, after, id)`:**
1. It first calls `observe(before, after, true)`, as `record` does, so the arrival is the connection's own edit for
   every step's guards: every live `object` entry refreshes its guard (as today for own edits), and a live unit entry
   refreshes its guard only when its `after` equals the unit's new value (as today). So a later step of this
   connection whose entry holds a unit the arrival changed keeps its old guard and is **stale**: a move made while the
   card loaded has a `geometry` entry (`x`, `y`, `width`, `height` together) whose `after` holds the loading size, so
   when the finish changes the card's size that entry is stale. Undo of that step follows the existing rule: only its
   entries whose guards still hold are reverted, and when none holds, Undo answers `changed_by_others` (today's
   notice) and the step is gone. When the finished size equals the loading size (306 × 288), the adapter writes no new
   `geometry` and the move undoes as usual.
2. It looks for the newest step in `past` holding a live entry `{ id, key: "object", before: null }` (the paste that
   added the card). If there is one, it sets that entry's `after` to its old value with the finish keys (`title`,
   `description`, `site`, `asset`, `state`, `layout`, `width`, `height`) taken from the card in `after`, keeping the
   old value's `x`, `y`, `order` and every other key (`x` and `y` shifted left and/or up just enough when the new
   size would cross the document bounds), and returns `true`. Otherwise it returns `false`.
3. Either way it adds **no step**, leaves `future` and the current edit group as they are, and the arrival is never an
   undo step of its own: no Undo or Redo ever reverts it.

So the outcomes are (each checked under **Verification**):
- **paste → arrival → Undo → Redo:** the paste's step, its guard refreshed by step 1, removes the finished card;
  Redo's step is computed from the board as Undo left it (as today), so Redo restores the finished card, under a
  fresh `id` (as every hosted restore).
- **paste → move → arrival → Undo → Undo → Redo → Redo:** when the finish changed the size, Undo 1 answers
  `changed_by_others` and the move's step is gone; Undo 2 removes the finished card; Redo 1 restores it finished at
  its moved place under a fresh `id`; Redo 2 has nothing to redo. A move made during loading may therefore no longer
  undo after the arrival: accepted.
- **paste → Undo before the arrival:** the card is removed; the arrival finds no card and writes nothing. Redo
  restores the loading card under a fresh `id`, which no arrival ever finds: it stays `loading` (no new request) and is
  drawn link-only once 20,000 ms are past its `requestedAt`.
- **paste → Change back to text → Undo → arrival (hosted):** the conversion removed the card and Undo restored it
  under a fresh `id`, so the arrival's gate finds no card with its `id`, uploads nothing if it has not yet uploaded,
  and writes nothing (the arrival is **dropped**); the restored card stays `loading`, follows the 20,000 ms rule and
  is never fetched again. (On a single-user board the same sequence **applies** the arrival, because local Undo
  restores the same `id`: interaction v52 and web modules v50.)
- **a concurrent move by another client and the arrival:** both outcomes under **Concurrent edits to a card**.

Another person's steps are unaffected beyond today's rule: for them the arrival is a remote edit, which kills their
entries for the units it assigned, as any remote edit does. The single-user board's local history follows
interaction v52 and web modules v50 instead (its restores keep the card's `id`).

Version previews, version restore and the history list read videos and link cards like any other object. A version
restore is never refused for an asset the room does not hold: a video whose first frame is missing, or a card whose
thumbnail is missing, shows the web app's missing-picture box, and one whose video is missing shows its first frame
and fails to load when someone presses play (interaction v50). Neither is checked by later edits that leave it as it
is. A restored `loading` card stays `loading` and follows the 20,000 ms rule.

## The codec

`readBoard` reads a video's keys and a link card's keys through the type registry, as it reads every type's. A
card's `asset` is stored in its object map as the hash or as `null`; an absent `asset` key reads as `undefined`, which
document v22 refuses. In the document adapter (`packages/board-sync/src/document-adapter.ts`), stale keys are removed
in one place only: the object loop of its board writer, **after** the table branch has returned (a table's object
map is written by `writeTable` and never touched by this removal) and never on the board map or a `pageMap` entry (a
page's `name` lives there and is untouched). In that place:
- a **video** keeps `asset`, `poster`, `pixelWidth`, `pixelHeight`, `durationMs`, `name` and `description` and
  loses `text`, `style`, `marks`, `ends` and `connectorStyle`, and also `url`, `title`, `site`, `layout`, `state`
  and `requestedAt`;
- an **image** keeps its keys as today and loses `poster`, `durationMs` and `name` as well, and also `url`,
  `title`, `site`, `layout`, `state` and `requestedAt`;
- a **link card** keeps `url`, `title`, `description`, `site`, `asset`, `layout`, `state` and `requestedAt` and
  loses `text`, `style`, `marks`, `ends`, `connectorStyle`, `pixelWidth`, `pixelHeight`, `poster`, `durationMs` and
  `name`;
- every **other** non-table type loses `asset`, `pixelWidth`, `pixelHeight`, `description`, `poster`,
  `durationMs` and `name`, as it loses the first four today, and also `url`, `title`, `site`, `layout`, `state` and
  `requestedAt`.

This removes `name` and `title` only from object maps: a page's `name` lives in its `pageMap` entry, the board's
`title` in the board map, and a table's maps are written by `writeTable`, and none of them is touched.

No frame, presence key, comment, vote or timer rule changes. A video is one object for presence selections,
comment anchors and vote targets (`voting: true`); so is a link card (`voting: true`). Playing a video sends
nothing: no frame, presence key or edit. Opening a card's link sends nothing to the room either. A preview request
is an HTTP call to the server ([API v16](0003-api-v16.md)), never a socket frame. Files never travel in a socket
frame: the 1 MiB message limit and the 2 MiB stored document limit are unchanged, and a video or a link card adds
only its document keys to them.

## Verification

In addition to v17's checks: a version 16 client update with a card accepted; a version 15 document holding a card
refused `invalid_document`; a stored storage 9 room at schema 15 upgraded to 16 by the schema-only step with no
edits row; a history version at 16 read, and a version 15 capture with its 16 upgrade causing no new capture; the
codec reading a card with `asset: null` and with a hash, and refusing one with no `asset` key; the adapter's stale-key
removal for each row above; the edit check for a card added with a held picture (accepted), with an unheld hash, a
video hash or a non-picture asset (`asset_missing`), with `asset: null` (accepted), and an unchanged card on a board
whose thumbnail was cleared (accepted); `requireHeldMedia` for the same cases; `SharedUndo.amend` adding no step in every case and returning `true` when it
finds the paste's live add entry (whose `after` then holds the finish keys and keeps its `x` and `y`, shifted only at
the document bounds) and `false` otherwise; the adapter writing an arrival's `geometry` and finish keys as one update;
each **hosted** outcome above through a real `BoardSession` (`edit` with and without `arrivalOf`, then `undo` and
`redo`): paste → arrival → Undo → Redo; paste → move → arrival (size changed) → Undo (`changed_by_others`) → Undo
→ Redo → Redo (`nothing_to_undo` for the last); the same with a finished size of 306 × 288 (the move undoes); paste →
Undo before the arrival → arrival (nothing written) → Redo (a fresh `id`, still `loading`); paste → Change back to
text → Undo → arrival (a fresh `id`, the arrival dropped: nothing uploaded or written, the card stale after 20,000 ms
with no new request); another connection's step on the card killed by the arrival, as today; and `edit` without
`arrivalOf` recording exactly as before. **Refusals:** an arrival refused synchronously (`message_too_large`) and one
refused by the room are each matched by `arrivalOf` on the request, show no toast, leave `HostedBoard.edit`'s result
as today (`true` for the synchronous case), make `arrivalRefused` answer `true` once, and lead to exactly one silent
link-only retry; a refused retry writes nothing more; a refusal of a request without `arrivalOf` shows today's toast.
**Two clients** on one room (the paster and another editor, neither having seen the other's edit): the other's move
of the loading card and the paster's arrival, delivered to the room in **both orders** (move first, arrival first):
the room accepts both updates each time, the merged card is valid, and it is one of the two accepted outcomes under
**Concurrent edits to a card** (the arrival's rectangle, or the moved place at 306 × 288 with the finish keys), the
same on both clients after they sync.
