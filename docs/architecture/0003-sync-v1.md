# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v1 (2026-10-30)

Status: Draft for 0003-W1 v1. It defines the room connection that the join route opens
([API contract](0003-api-v1.md)): the messages, when an edit counts as saved, the limits, and
the close codes. The room's storage is in the
[hosted persistence contract](0003-hosted-persistence-v1.md).

## Framing

Every message in either direction is one WebSocket text frame holding one JSON object with a
`kind`. Yjs data travels as base64 (standard alphabet, with padding) of the bytes Yjs encodes.
Unknown kinds and malformed JSON are refused with `bad_message`; the connection stays open.

| Direction | `kind` | Fields |
| --- | --- | --- |
| room → client | `joined` | `role`, `epoch`, `revision`, `update` (the whole board as one Yjs update) |
| client → room | `edit` | `epoch`, `requestId` (1–100 characters), `update` |
| room → client | `received` | `requestId` |
| room → client | `saved` | `requestId`, `revision` |
| room → client | `refused` | `requestId` (when the refusal is about an edit), `reason`, and `needed` for `role_too_low` |
| room → other clients | `update` | `revision`, `update` |
| room → client | `resync` | `reason`, `stateVector` (the room's Yjs state vector) |
| client → room | `renew` | `token` ([identity contract](0003-identity-v1.md)) |
| room → client | `renewed` | `expiresAt` |

`revision` counts saved edits on the board, starting at 0 for a new board.

## Joining

The room sends `joined` only after the person's role is known and the ticket is valid. Before
that it sends nothing from the board: every refused join, including one on a locked room, is
answered over HTTP before the WebSocket upgrade (API contract). When a restore locks a room,
every open connection is closed with 4423.

## Editing

An editor sends `edit` with the epoch it joined under and a request ID it has not used for a
different edit. The room handles one message at a time and:

1. Refuses the edit if the person's role is `viewer` (`role_too_low`, `needed` `editor`) or the
   epoch is not the person's current epoch (`epoch_changed`). Nothing is stored.
2. Applies the update to a copy of the board. If Yjs reports that the update depends on changes
   the room does not have yet, the edit is incomplete: it waits (see "Waiting edits") and the
   room replies `received`. `received` never means saved.
3. Checks the complete result: the update uses only the board's own Yjs fields; the resulting
   document passes [document v11](0001-document-v11.md)'s validation, size limit and
   before/after rule against the board before the edit; and it adds no image object. A failure
   is `refused` with `invalid_update`, `invalid_document`, `document_too_large`,
   `invalid_transition`, `identifier_reused` or `images_not_supported`. Nothing is stored.
4. Stores the edit, its receipt and the new revision in one storage transaction, then replies
   `saved` and sends `update` to the board's other connections. No other connection sees an
   edit before it is stored.

After step 4 the room tries the waiting edits again in the order they arrived.

**Retrying.** If the same person sends the same request ID with the same update again, the room
answers with the stored `saved` and changes nothing. The same request ID with a different
update is refused with `request_id_reused`.

## Waiting edits

An incomplete edit waits in storage, tied to its connection. Each connection may have at most
**64** waiting edits and **4 MiB** of waiting message bytes (counting each whole incoming
message), and each edit waits at most **30 seconds**. When an edit would go past a limit, or a
waiting edit's 30 seconds run out, the room deletes every waiting edit of that connection and
sends `resync` with reason `waiting_count`, `waiting_bytes` or `waiting_timeout`. None of them
is saved. The client answers by sending, as a new `edit`, everything its board has that the
room's state vector lacks.

Waiting edits and their deadlines survive the room being evicted from memory. When a
connection closes, or the Node server restarts and its connections drop, that connection's
waiting edits are deleted; the client rejoins, receives `joined`, and sends again whatever was
not `saved`.

## Size

The limit applies to messages the room receives. The room's own messages are not limited by
it: `joined` carries the whole board (about 2 MiB of Yjs data for the largest board document v10
allows), and an `update` is never larger than the edit it relays. Both runners accept outgoing
messages of that size.

A received message over **1 MiB** (1,048,576 bytes) is refused with `message_too_large` and the
connection stays open. A frame larger than the transport accepts (more than 1 MiB plus
64 KiB on the Node server; 32 MiB on Cloudflare) may instead be closed by the WebSocket layer
with the standard code 1009 before the room sees it.

## Close codes

| Code | Meaning | The client should |
| --- | --- | --- |
| 1009 | Frame too large for the transport | Send smaller edits |
| 4401 | The token expired, or a renewal failed or named another person | Get a fresh token and a new ticket, then rejoin |
| 4403 | The person's access was lowered or removed. In this version only replay sends it ([access contract](0003-access-v1.md), "Replay") | Stop, and get a new ticket only if the person still has a role |
| 4409 | The person's access changed (raised) | Get a new ticket and rejoin; the new role applies |
| 4423 | A restore locked the room while the connection was open | Retry later with a new ticket |
