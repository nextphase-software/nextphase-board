# 0003 — Server API contract

CONTRACT VERSION: 0003 API v14 (2026-11-24)

Status: Draft for 0012-W4 v1. Replaces [API v13](0003-api-v13.md), whose routes, authentication, origins,
tickets, capacity, lifecycle ordering, socket rules, template routes, picture types, header sizes and error
bodies remain word for word except as below. This version lets the two asset routes of API v13 also store and
serve a team board's **videos**. Every body that is not a video, and every picture `GET`, keeps exactly today's
path, order and answers; only a video is **streamed** from the request to the board's room and back, so no Worker
or room ever holds a whole video. No route is added. Where videos are kept is
[hosted storage v14](0003-hosted-storage-v14.md); who may use the routes is [access v15](0003-access-v15.md); how
each runner carries the streams is [self-host runner v9](0003-self-host-runner-v9.md).

## Terms

- An **asset** is a picture or a video. A **hash** is 64 lowercase hexadecimal characters: the SHA-256 digest of
  an asset's bytes, as [document v21](0001-document-v21.md)'s image `asset`, video `asset` and video `poster`
  keys hold it. A video's `poster` (its first frame) is a JPEG picture.
- The **head** of a request body is its first 64 bytes, or the whole body when it is shorter, however the body's
  chunks split them.
- The **picture signature** of a head is read by a new signature-only classifier, `pictureSignature(head)` in
  `packages/board-room/src/pictures.ts`. Its conditions are, byte for byte, the conditions under which today's
  `pictureHeader` enters each of its four branches (`pictures.ts`, the PNG, GIF, JPEG and WebP tests), with no size
  read; this is the one routing definition, which the web app cites (interaction v50). Today's picture validators
  (`pictureHeader` and the browser's own picture checks) stay as they are.

  | Signature | Conditions on the head |
  | --- | --- |
  | PNG | At least 24 bytes; bytes 0–7 `89 50 4E 47 0D 0A 1A 0A`; bytes 12–15 `49 48 44 52` (`IHDR`) |
  | GIF | At least 10 bytes; bytes 0–5 `47 49 46 38 37 61` or `47 49 46 38 39 61` (`GIF87a`, `GIF89a`) |
  | JPEG | Bytes 0–2 `FF D8 FF` |
  | WebP | Bytes 0–3 `52 49 46 46` (`RIFF`) and bytes 8–11 `57 45 42 50` (`WEBP`) |

- A **video type** is read from the head by `videoType(head)` (beside it), never from the request's
  `Content-Type` or a name:
  - MP4 and MOV: bytes 4–7 are `ftyp` (`66 74 79 70`). The major brand, bytes 8–11, `qt  ` (`71 74 20 20`)
    gives `video/quicktime`; any other brand gives `video/mp4`.
  - WebM: bytes 0–3 are `1A 45 DF A3`, and after them the EBML DocType element appears: the bytes `42 82`, then an
    EBML size of 4 (the byte `84`, or the eight bytes `01 00 00 00 00 00 00 04`), then the four bytes `webm`
    (`77 65 62 6D`), all of it inside the head. This gives `video/webm`.
  - Anything else is not a video: for example a QuickTime file that starts with `moov`, `mdat`, `wide` or `free`
    instead of `ftyp`, or a Matroska file whose DocType is `matroska`.

  This is [storage v4](0001-storage-v4.md)'s video header, which the web app reads in `apps/web/src/video.ts`
  ([interaction v50](0001-interaction-v50.md)).
- A head is a **video head** when it has a video type **and no picture signature**. Picture signatures win: a
  RIFF/WebP head whose bytes 4–7 (the RIFF size field) happen to read `ftyp` is a picture, never a video. The web
  app routes a file with the same precedence (interaction v50).

## Routes

| Route | Body | Success | Refusals |
| --- | --- | --- | --- |
| `PUT /boards/:board/assets/:hash` | The picture's or video's bytes, raw (any `Content-Type`; the web app sends `application/octet-stream`) | 201 `{asset, type, bytes}` when the asset was stored now; 200 with the same body when the board already held it (its upload time is renewed, [hosted persistence v12](0003-hosted-persistence-v12.md)) | 404 `not_found` (path, access, lifecycle); 403 `role_too_low`, `needed: "editor"` (a viewer); 413 `body_too_large` (a non-video body over 20,971,520 bytes, a video over 52,428,800); 400 `unsupported_picture` (a non-video body that is empty, has no picture signature or has an unreadable header size); 400 `picture_too_large`; 400 `picture_hash_mismatch` (the bytes' SHA-256 is not `:hash`); 409 `board_pictures_full`; 409 `board_videos_full`; 503 `service_unavailable` |
| `GET /boards/:board/assets/:hash` | — | 200, the asset's bytes exactly as stored, with `Content-Type` its stored type (a picture type or a video type), `Content-Length`, `Cache-Control: private, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff`. A picture is sent as today; a video is **streamed** part by part | 404 `not_found` (path, access, lifecycle, or an asset the board does not hold); 503 `service_unavailable` |

`asset` is the hash, `type` the stored type and `bytes` the stored byte count.

`GET` has no ranges: a `Range` request header is ignored, the answer is always the whole file with 200, and no
`Accept-Ranges` header is sent. A video stream that cannot finish (the video was removed by clean-up while it was
being sent, hosted storage v14) ends in error, so the response is cut short of its `Content-Length` and the client
sees a failed download.

**Checks run in this order** for both routes; the first that applies answers, before anything is stored (except
the clean-up that a `board_pictures_full` or `board_videos_full` refusal commits, hosted storage v14):

1. to 4. API v13's steps 1 to 4, unchanged: bearer authentication, the lifecycle gate, the path values, and
   access through `authorize()` (`PUT` needs `"editor"`, before any body byte is read; `GET` any role).
5. `PUT` only, the head: a new `head(c, 64)` in `routes/common.ts` takes the request body's reader and reads chunks
   until it holds 64 bytes or the body ends (a head split across several chunks is joined), then returns the head
   with a **replay stream** of the whole body from byte 0: first the bytes already read (at most 64 plus the rest
   of the last chunk read), then, one pull at a time, the reader's remaining chunks, never read ahead. Cancelling
   the replay stream cancels the reader; reading it to its end releases the reader. The route always either reads
   the replay stream to its end or cancels it.
   - A **video head** takes the **video path** (step 7).
   - Every other body, an empty one included, takes the **picture path** (step 6) with today's order and answers:
     an unknown body over 20,971,520 bytes is still 413 before it is refused 400.
6. **Picture path**, API v13's steps 5 and 6 unchanged, reading the replay stream: the whole body read raw with
   the limit 20,971,520 (413 `body_too_large`), then `unsupported_picture` (no picture signature or an unreadable
   header size), `picture_too_large`, `picture_hash_mismatch`, then the room's picture store. Its 409
   `board_pictures_full` now counts only the board's held assets **of picture types** (first frames included):
   with this one they may not exceed 52,428,800 bytes. Videos never count toward it.
7. **Video path**: the replay stream goes to the room unread (`storeVideo`, runner v9), with the video type. The
   room, in this order (hosted storage v14 says how):
   1. **admits** the call in its ordered queue as export is admitted (role looked up again: owner or editor;
      lifecycle and recovery gates), runs the clean-up and notes whether the board holds the hash. For a hash it
      does not hold, 409 **`board_videos_full`** when the held videos, the bytes already staged by this board's
      other uploads in progress and this upload's first byte would exceed **104,857,600** bytes;
   2. **receives** the whole body in chunks, hashing as it goes: a video it does not hold is written in 1 MiB
      staged parts; a held one is only counted and hashed (drained). Once more than **52,428,800** bytes have
      arrived, 413 `body_too_large` (the stream is cancelled). For a video it does not hold, 409
      `board_videos_full` as soon as a part would take the board's current held videos plus every upload's staged
      bytes past 104,857,600 (re-read at each part write). A body
      that ends early or ends in error stores nothing;
   3. 400 `picture_hash_mismatch` when the SHA-256 of the bytes received is not `:hash`. A second upload of a hash
      that another upload is staging (its **owner**) only drains and hashes its body, then waits for the owner: if
      the owner stored the video, it finishes as an upload of a held hash (step 4, 200); if the owner failed or was
      refused, it answers 503 `service_unavailable` and stores nothing;
   4. **finishes** in its ordered queue, after the role, lifecycle and recovery checks of step 1 again (403
      `role_too_low` or 404 `not_found` exactly as for a new upload) and after clean-up: if the board holds the
      hash, it renews its upload time and answers 200; otherwise 409 `board_videos_full` when the held videos with
      this one would exceed 104,857,600 bytes; otherwise the video is stored, 201.

   An upload in progress when the board is trashed answers 404 `not_found`; one in progress when the board is
   restored from Trash, restored from a backup or to a time, or erased answers 503 `service_unavailable` (hosted
   storage v14, "The upload registry"). A body that stalls for 60,000 ms answers 503.

   An upload of a held hash therefore answers 200 only after its whole body has arrived within the limit, hashed
   to `:hash`, and the caller still has the right. **No refusal renews anything**, and nothing of a refused or
   failed video stays stored. A body that ends in error (the client went away) answers 503
   `service_unavailable` if anyone is still listening.

Any other storage or room failure is 503 `service_unavailable` and stores nothing of the asset. Error bodies use
the existing `errorBody` shape.

| Limit | Picture path | Video path |
| --- | --- | --- |
| One file | 20,971,520 bytes (413 `body_too_large`) | 52,428,800 bytes (413 `body_too_large`) |
| A board's held assets of that kind, distinct hashes | 52,428,800 bytes of picture types (409 `board_pictures_full`), first frames included | 104,857,600 bytes of video types, with the bytes staged by uploads in progress (409 `board_videos_full`) |
| Header | Longer side at most 4,096 (400 `picture_too_large`) | No size is read |

Both are below the 100 MB request body limit of a Cloudflare zone on the Free or Pro plan
([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).

**CORS** is unchanged: the allowed methods already include `PUT`, the allowed request headers stay
`Authorization, Content-Type` (the web app's video upload sends only these, hosted storage v14), and no header is
exposed: `Content-Length`, which the web app reads for its download progress, is a CORS-safelisted response
header. Only the two asset routes carry the caching headers above; no other route changes.

## Board import and templates

The board import route (`POST /workspaces/:workspace/boards`, 13 MiB body) accepts a document of declared schema
version 13, 14 or **15** and upgrades it to 15 ([sync v17](0003-sync-v17.md)); it answers 400
`images_not_supported` for a document holding an `image` **or a `video`** object (the reason code is unchanged).
The template routes refuse an `image` or `video` object with 400 `bad_request` and validate template objects
inside a version 15 wrapper ([lifecycle v7](0006-board-lifecycle-v7.md)). Bringing a board file or a template with
pictures or videos into a team workspace is later work. No other route, socket frame, ticket or joined field
changes.
