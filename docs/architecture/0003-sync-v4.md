# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v4 (2026-11-01)

Status: Draft for 0003-W4 v1. It replaces [sync v3](0003-sync-v3.md) and changes two things
only: an edit sent by the shared client may join the connection's previous undo step ("Grouped
edits" under "Undo on a shared board", used so that typing in one note is one step), and "Waiting
edits" no longer says that a client sends unsaved edits again after a disconnect (a client may;
the shared client does not). Every other rule, message, limit and close code is v3's, word for
word. It defines the room connection that the join route opens
([API contract](0003-api-v4.md)): the messages, when an edit counts as saved, the limits, and
the close codes. The room's storage is in the
[hosted persistence contract](0003-hosted-persistence-v3.md); who may do what is in the
[access contract](0003-access-v4.md). The room itself does not change: nothing in this version
reaches the server.

## Framing

Every message in either direction is one WebSocket text frame holding one JSON object with a
`kind`. Yjs data travels as base64 (standard alphabet, with padding) of the bytes Yjs encodes.
Unknown kinds and malformed JSON are refused with `bad_message`; the connection stays open.

| Direction | `kind` | Fields |
| --- | --- | --- |
| room → client | `joined` | `role`, `epoch`, `revision`, `update` (the whole board as one Yjs update), `self`, `present` ([presence contract](0004-presence-v1.md), "Joining") |
| client → room | `edit` | `epoch`, `requestId` (1–100 characters), `update` |
| room → client | `received` | `requestId` |
| room → client | `saved` | `requestId`, `revision`, and `update` when the room changed the edit (see "Editing", step 6) or answers a retry |
| room → client | `refused` | `requestId` (when the refusal is about an edit), `reason`, and `needed` for `role_too_low` |
| room → other clients | `update` | `revision`, `update` |
| room → client | `resync` | `reason`, `stateVector` (the room's Yjs state vector) |
| client → room | `renew` | `token` ([identity contract](0003-identity-v3.md)) |
| room → client | `renewed` | `expiresAt` |
| client → room | `presence` | `cursor`, `selection`, `view`, `active` (presence contract) |
| room → other clients | `present` | the stamped presence (presence contract, "What the room relays") |
| room → other clients | `left` | `connection` |

`revision` counts saved edits on the board, starting at 0 for a new board. Presence messages
never change it.

## Joining

The room sends `joined` only after the person's role is known and the ticket is valid. Before
that it sends nothing from the board: every refused join, including one on a locked room or a
full one, is answered over HTTP before the WebSocket upgrade (API contract). When a restore
locks a room, every open connection is closed with 4423.

## Property units

The room and the shared client treat each object's fields in the units the board's Yjs mapping
already stores ([web modules v24](0001-web-modules-v24.md); `packages/board-sync/src/document-adapter.ts`).
Each unit is one value: two edits to different parts of one unit are two changes to the same
unit.

| Unit | Holds |
| --- | --- |
| `geometry` | `x`, `y`, `width` and `height` together |
| `style` | `color`, `textSize` and `align` together |
| `marks` | the whole list of text marks |
| `ends` | a connector's `from` and `to` together |
| `connectorStyle` | a connector's style fields together |
| `text` | the text, which merges by character (below) |
| each other field | `order`, `group`, `section`, and each extra field an object type defines (for example a shape's `fill`), one unit each |
| `title` | the board's title |

`id`, `type` and `generation` never change while an object exists ([document v11](0001-document-v11.md)).

## Two people, one board

Edits are saved one at a time in the order the room handles them. The result on every connection
is the same board, under these rules:

1. **Different objects, or different units of one object:** both changes are kept.
2. **Text in one object:** merges by character. The client writes only the part of the text
   that changed (see "Text writes"), so two people typing in one note at the same time keep both
   their typing. Where both insert at the same place, the order of the two insertions is Yjs's
   own and the same on every connection.
3. **The same unit (other than text):** the edit the room saves last wins, whichever client Yjs
   itself would have ordered first.
4. **A delete and a change to the deleted object:** the delete wins; the change is saved but
   has no effect.
5. **A merge that would not be valid** is repaired by the room (see "Repairs") when one of the
   repairs applies, and refused otherwise.

A saved edit is lost only by a later saved change to the same unit, by a delete of its object,
or by a repair.

## Text writes

When the client writes a text object, it compares the text it holds with the new text by
grapheme cluster (`Intl.Segmenter` with granularity `grapheme`): it first keeps the longest
common start, then the longest common end of what remains of both texts after that start (the
two never overlap: `aaa` to `aa` keeps `aa` as the start and deletes the last cluster), deletes
only the clusters between them and inserts only the new clusters, at the UTF-16 offsets Yjs
uses. It never splits a cluster: a surrogate pair, a
letter with combining marks or a joined emoji is kept or replaced whole. Nothing in the saved
document, the Yjs mapping or the wire layout changes; boards kept in a browser use the same code
and save exactly the same documents as before.

## Editing

An editor sends `edit` with the epoch it joined under and a request ID it has not used for a
different edit. The room handles one message at a time and:

1. Refuses the edit if the person's role is `viewer` (`role_too_low`, `needed` `editor`) or the
   epoch is not the person's current epoch (`epoch_changed`). Nothing is stored.
2. Applies the update to a copy of the board. If Yjs reports that the update depends on changes
   the room does not have yet, the edit is incomplete: it waits (see "Waiting edits") and the
   room replies `received`. `received` never means saved.
3. **Last saved wins.** For every unit (other than `text`) that the update assigns, the room
   makes the update's value the current value in the copy, even where Yjs orders a concurrent
   assignment ahead of it, and even when the two values are equal. A unit of an object that is
   not in the copy (deleted) is left deleted.
4. **Repairs** (below), on the copy.
5. Checks the complete result: the update uses only the board's own Yjs fields; the resulting
   document passes [document v11](0001-document-v11.md)'s validation, size limit and
   before/after rule against the board before the edit, and the identifier record; and it adds
   no image object. A failure is `refused` with `invalid_update`, `invalid_document`,
   `document_too_large`, `invalid_transition`, `identifier_reused` or `images_not_supported`.
   Nothing is stored.
6. Stores the edit, its receipt and the new revision in one storage transaction, then replies
   `saved` and sends `update` to the board's other connections. The stored edit and the `update`
   sent are the room's own update: the edit's update together with every change steps 3 and 4
   made, as one Yjs update. When steps 3 or 4 changed anything, `saved` carries that same
   update, so the editor's board becomes the room's; otherwise `saved` has no `update`. No other
   connection sees an edit before it is stored.

After step 6 the room tries the waiting edits again in the order they arrived.

**Retrying.** If the same person sends the same request ID with the same update again, the room
answers `saved` with the stored revision and, as `update`, the whole current board as one Yjs
update, and changes nothing. The receipt is matched by the SHA-256 of the update the client sent,
not of the room's own update. The same request ID with a different update is refused with
`request_id_reused`.

## Repairs

Two edits that are each valid can merge into a board that is not: two new objects with the same
`order`, marks that run past a text another person shortened, a connector to an object another
person deleted, an object in a section another person deleted. In step 4 the room repairs the
copy, in this order, before it checks it:

1. **Deleted objects.** A connector whose `from` or `to` names an object not in the copy is
   removed, and its generation retired, as when a person deletes a connected object on their own
   board. An object whose `section` names an object not in the copy gets `section` `null`.
   `group` is never changed. A connector this edit itself added and a repair removed still has
   its `id` and `generation` checked against the identifier record like any new object (a
   clash is refused with `identifier_reused`), and both are added to the record in the same
   storage transaction as the edit, so that ID never returns.
2. **Marks.** Each text object's marks become `normalize(marks, length)` from
   `packages/board-rules/src/marks.ts`, with its text's length counted as
   [document v10](0001-document-v10.md) counts it: marks are cut to the text, marks left empty
   are dropped, and marks that are already valid stay exactly as they are.
3. **Order.** The objects are sorted by `order`; objects with the same `order` are sorted with
   the objects that were in the board before this edit first, then by `id`; then each object's
   `order` becomes its place in that list, from 0.

A repair changes nothing on a board that needs none. If the copy still fails step 5 after the
repairs (for example more than 250 objects, or a text over its limit), the edit is refused as
step 5 says.

## Waiting edits

An incomplete edit waits in storage, tied to its connection. Each connection may have at most
**64** waiting edits and **4 MiB** of waiting message bytes (counting each whole incoming
message), and each edit waits at most **30 seconds**. When an edit would go past a limit, or a
waiting edit's 30 seconds run out, the room deletes every waiting edit of that connection and
sends `resync` with reason `waiting_count`, `waiting_bytes` or `waiting_timeout`. None of them
is saved. The client answers by sending, as a new `edit`, everything its board has that the
room's state vector lacks.

When the person's role on the board falls (access contract, "Taking access away"), the room
deletes the waiting edits of every connection the person holds in the same storage step that
lowers the role, before it handles any other message; none of them is saved, and no `resync` is
sent, because the connection is then closed with 4403.

Waiting edits and their deadlines survive the room being evicted from memory. When a
connection closes, or the Node server restarts and its connections drop, that connection's
waiting edits are deleted; the client rejoins and receives `joined`. A client may then send
again what was not `saved`; the shared client does not (see "The shared client", "Closing").

## Undo on a shared board

Undo and redo on a hosted board take back only the steps of the connection that made them,
property unit by property unit. The shared client keeps them; the room sees an undo as an
ordinary edit.

- **What a step records.** For every unit the connection's own edit changed, the value before
  and after, and the Yjs identity of the assignment it made (for `text`, the identities of the
  text's characters and deletions); for every object it added or deleted, the whole object. At
  most 100 steps are kept; the oldest goes first. Each connection of a person has its own steps.
- **Someone else changed it since.** A unit is undone only if its current Yjs assignment is
  still the step's guard. If anyone else assigned it since, even the same value, it is left as
  they left it. The guard follows the connection's own later assignments: when the connection
  itself assigns a unit again (by an edit, an undo or a redo), and when the room's own update in
  `saved` reassigns a unit the connection had assigned to the same value (step 3 or 4 of
  "Editing"), every older step of that connection whose recorded value for that unit equals the
  value now current takes the new assignment as its guard, but only while its guard is still
  live. A step's guard for a unit dies for good as soon as any other connection assigns that
  unit after it, even to the same value, and nothing later revives it: with A moving N to G, B
  then setting the same G, A moving N to H and undoing back to G, A's first move can no longer be
  undone. For `text`, any change by anyone else to that object's text since leaves the
  whole text as it is; typing still merges by character as above. An added object is removed by
  undo only if nobody else changed any of its units since. The rest of the step is still undone.
- **Bringing an object back.** Whenever undo or redo puts back an object that is no longer on
  the board (undo of a delete, or redo of an add that an undo removed), the object gets a new
  `id` and a new `generation` (document v11 and the identifier record forbid reusing either), in
  its old place in the order. Connectors and section members put back by the same step point to
  the new IDs; a connector put back whose other end no longer exists stays off the board, and an
  object put back whose section no longer exists gets `section` `null`. The connection's older
  steps that name the old ID are made to name the new one.
- **Grouped edits.** An edit may carry a group: a non-empty string the caller chooses, kept by
  the client and never sent to the room. When an edit's group equals the group of the edit that
  made the connection's newest step, and nothing has added a step, undone, redone or cleared the
  steps since, the edit does not make a new step: it joins that step. Only unit changes join: an
  edit that adds or deletes an object never joins a step, even with the same group; it makes its
  own step as an ungrouped edit would, and the next edit of that group starts a new step. For
  each unit, the joined step keeps the value before the group's first edit that changed it, and
  takes the value after, and the guard, of the group's latest edit that changed it; a unit first
  changed by a later edit of the group is added with its value before that edit; a guard that died
  within the group stays dead. A joined step is one step: it counts once toward the 100, and undo
  and redo treat it as any other step. An edit with no group, or with another group, makes a new
  step as before.
- **Redo** reapplies only what the undo actually changed, with the same check against later
  changes by others. A new edit by the connection clears its redo steps.
- **Back to the present.** With nobody else editing, undo then redo leaves the board as it was
  before the undo, comparing every object and every unit of it, with each object that was put
  back compared under its new `id` and `generation` (and references to it mapped the same way);
  `retiredGenerations` only grows, so it is not part of this comparison.
- **A step that cannot be applied.** If an undo or redo would produce a board that fails
  [document v11](0001-document-v11.md)'s validation or before/after rule, nothing is sent and
  the step is dropped, with the reason `undo_invalid`. A step with nothing left to change sends
  nothing and is dropped, with the reason `changed_by_others`. With no step to undo or redo,
  nothing is sent, with the reason `nothing_to_undo`.

Undo of a board kept in a browser is unchanged.

## The shared client

`packages/board-sync/src/session.ts` is the client for one hosted board, with no screen. It
uses this protocol only, and reaches the network, the clock and timers only through what it is
given, so the web app, the Node server's tests and the Worker tests use the same code.

- **Joining.** It gets a ticket from the function it is given, opens the connection with the
  function it is given, and applies `joined`: the board, role, epoch, revision, its own presence
  and the others'.
- **Editing.** It applies an edit to its own board at once, sends it, and tracks each request as
  `sent`, `received`, `saved`, `refused` or `dropped`. `edit(board, group?)` takes an optional
  group for "Grouped edits"; the message sent is the same with or without one. It applies
  `update`, and the `update` of `saved` when present. It answers `resync` as "Waiting edits" says: every request then in
  state `received` (the room has just deleted those waiting edits) becomes `dropped`, and the new
  `edit` that carries their content is a new request, tracked like any other; a request still
  `sent` keeps waiting for its own answer. A viewer's edit, undo or
  redo is refused by the client itself with `role_too_low` and nothing is sent.
- **A refused edit.** Its board then holds a change the room refused, which cannot be taken out
  of a Yjs document. It marks that request `refused` with the room's reason and every other
  request not yet saved `dropped`, clears its undo and redo steps, closes the connection (code
  1000), gets a new ticket, joins again and takes the room's board from the new `joined`. Until
  then, edits, undo and redo are refused by the client with `join_required`. The client never
  sends an `edit` message over 1 MiB: it treats such an edit as refused with
  `message_too_large` without sending it. A `refused` with no `requestId` whose reason is not a
  presence reason (`presence_too_large`, `presence_fields`, `presence_selection_limit`,
  `bad_presence`) cannot be matched to a request: the client reports it and rejoins as above,
  every request not yet saved becoming `dropped`; a presence refusal is only reported.
- **Presence.** It sends a presence when asked, at most one every 100 milliseconds: a request
  that comes sooner is held, and when the 100 milliseconds have passed the latest held one is
  sent. While joined, once it has sent a presence, it sends its last presence again whenever
  15 seconds pass without one sent. It refuses, without sending, a presence that breaks the presence contract's
  "What the client sends" or "Bounds" (`presence_too_large`, `presence_selection_limit`,
  `bad_presence`). It keeps the others' presence from `joined`, `present` and `left`.
- **Closing.** A close by the room (1012, 1013, 4401, 4403, 4409, 4423) is reported with its code; the client
  does not rejoin by itself, and its requests not yet saved become `dropped`; it never sends them
  again. Recovering work across a disconnect is not in this version.

## Size

The limit applies to messages the room receives. The room's own messages are not limited by
it: `joined` carries the whole board (about 2 MiB of Yjs data for the largest board document v10
allows), a `saved` that answers a retry carries the whole board too, and an `update` or a
`saved` with `update` is never larger than the edit plus the room's own changes. Both runners
accept outgoing messages of that size.

A received message over **1 MiB** (1,048,576 bytes) is refused with `message_too_large` and the
connection stays open. A frame larger than the transport accepts (more than 1 MiB plus
64 KiB on the Node server; 32 MiB on Cloudflare) may instead be closed by the WebSocket layer
with the standard code 1009 before the room sees it. Presence messages have their own, smaller
limit (presence contract, "Bounds").

## Close codes

| Code | Meaning | The client should |
| --- | --- | --- |
| 1009 | Frame too large for the transport | Send smaller edits |
| 1012 | The connection was opened by a server version before this one, so it has no label or colour (hosted persistence contract, "Storage version") | Get a new ticket and rejoin |
| 1013 | The connection opened after its join's hold ended and the board was full ([presence contract](0004-presence-v1.md), "Bounds") | Get a new ticket and try again later |
| 4401 | The token expired, or a renewal failed or named another person | Get a fresh token and a new ticket, then rejoin |
| 4403 | The person's access was lowered or removed, or the person was disabled ([access contract](0003-access-v4.md), "Taking access away" and "Replay"). Every edit sent after the room step was refused with `epoch_changed` and none was saved | Stop, and get a new ticket only if the person still has a role; a person lowered to `viewer` rejoins as a viewer |
| 4409 | The person's access changed (raised) | Get a new ticket and rejoin; the new role applies |
| 4423 | A restore locked the room while the connection was open | Retry later with a new ticket |

Before the room closes a connection with any of these codes, it sends `left` for it to the
board's other connections (presence contract, "What the room relays").

## Not in this version

Offline editing, recovering unsaved edits after a disconnect or a refusal, recovery screens and
hosted pictures.
