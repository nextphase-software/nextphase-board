# 0003 — Server API contract

CONTRACT VERSION: 0003 API v16 (2026-11-25)

Status: Draft for 0012-W5 v1. Replaces [API v15](0003-api-v15.md), whose routes, authentication, origins, tickets,
capacity, lifecycle ordering, socket rules, template routes, asset routes, staged import, template media, asset sizes,
picture and video types, header sizes, streaming and error bodies remain word for word except as below. This version
adds **link previews**: `POST /boards/:board/link-preview` for team boards and `POST /link-preview`, the server's one
public route, for single-user boards. Both answer from the fetcher of [link preview v1](0012-link-preview-v1.md),
which stores nothing. Who may call each route is [access v17](0003-access-v17.md); how each runner sets them up is
[self-host runner v11](0003-self-host-runner-v11.md). The new rules are in the section **Link previews (v16)** and in
the changed **Unchanged** section; everything else below is v15's text.

Media and schema rules elsewhere in the copied text are updated for link cards where marked "(v16)": a card's
non-null `asset` is a media hash of the picture kind, and board create or import accepts schema 13–16.

**Carried from v15 (2026-11-25):** v15 replaced [API v14](0003-api-v14.md). It lets a team workspace **import a board
file that holds pictures and videos** (a staged import whose board exists only from its finish step) and lets **team
templates hold pictures and videos** (a store per template). Where the files are kept is
[hosted storage v15](0003-hosted-storage-v15.md); who may use each route is [access v16](0003-access-v16.md); how each
runner keeps the new stores is [self-host runner v10](0003-self-host-runner-v10.md).

## Terms

- An **asset entry** is a JSON object with exactly the keys `hash` (64 lowercase hexadecimal characters), `type` (a
  picture type or a video type, API v14) and `bytes` (an integer from 1 to that kind's limit: 20,971,520 for a
  picture type, 52,428,800 for a video type).
- An **asset list** is an array of 1 to **1,000** asset entries with all `hash` values different.
- An **upload id** is a lowercase UUID chosen by the server (`crypto.randomUUID()`), never by the client. In a path,
  a value that is not a lowercase UUID is 404 `not_found`; in a body, 400 `bad_request`.
- **Media hashes** of a document or an object array: every image's `asset`, every video's `asset` and `poster`, and
  (v16) every link card's `asset` that is not `null` ([document v22](0001-document-v22.md): its assets, `assetsOf`).
  An image `asset` needs a picture held, a video `poster` a picture held as `image/jpeg`, a video `asset` a video
  held, and (v16) a card's thumbnail a picture held (the typed held check `requireHeldMedia` of
  [sync v18](0003-sync-v18.md)). An object **names media** when `assetsOf(o).length > 0`: an image, a video, or a
  card whose `asset` is not `null`; a card with `asset: null` names none. A card is not media in the sense of
  `isMedia` (document v22), but every rule of this contract about media hashes includes its thumbnail.
- New reason codes: **`upload_expired`** (410: the upload id is unknown to its store in this workspace, or expired; an
  erased store and one never opened answer the same), **`import_in_progress`** (409: another finish holds the import's
  claim, an upload holds its lease, or the board already exists) and **`upload_in_progress`** (409: another upload
  holds the staging's lease).
- **Precedence** on every new route: path ids (404) → the route's role check (403 / 404) → the store's 410 → the
  store's 403 (another person) → body and entry checks (400, 413) → budgets (409).

All new routes are registered in `apps/server/src/app.ts` after the existing `templates` routes, from two new files,
`apps/server/src/routes/imports.ts` and `apps/server/src/routes/template-media.ts`, except the sizes route, which is
registered in `apps/server/src/routes/pictures.ts`. Each needs a signed-in person (the existing bearer middleware) and
reads the person's role in its own call; no earlier step's answer counts.

## Staged board import

| Step | Route | Body (limit) | Checks, in order | Answers |
| --- | --- | --- | --- | --- |
| Open | `POST /workspaces/:workspace/imports` | `{ "assets": <asset list> }` (1,048,576, the default) | Workspace role editor or owner (`authorize(…, "workspace", "editor")`, as today's board create: a viewer or a workspace guest 403 `role_too_low`, a non-member 404); body shape exactly `["assets"]`; the asset list; the sums of `bytes` by kind within a board's budgets (picture types ≤ 52,428,800; video types ≤ 104,857,600); then `room(<new id>).openImport` | **201** `{ "import": "<upload id>" }`. 400 `bad_request`; 409 `board_pictures_full` / `board_videos_full` |
| Upload | `PUT /workspaces/:workspace/imports/:import/assets/:hash` | Raw bytes, as the board asset `PUT` of API v14 | Ids; workspace role as Open; `token = beginImport` (410, 403, 409 `upload_in_progress`, 400 for an undeclared hash); then exactly the board asset `PUT`'s head routing, limits, header checks and hash check of API v14 into `stageImportPicture` (whole) or `stageImportVideo` (streamed), each given the workspace and token; `endImport(…, token)` in a `finally` when the route fails before the store answered | **201** `{ asset, type, bytes }`, or **200** if the staging holds it. 410 `upload_expired`; 403 `role_too_low`; 400 `bad_request` (an entry mismatch); every refusal of API v14's asset `PUT` |
| Finish | `POST /workspaces/:workspace/boards` with the new optional key `import` | `{ "title", "document", "import" }` (13,631,488, unchanged) | As API v14 (role, shape now `["title","document"]` or `["title","document","import"]`, title, schema 13–16 (v16; 16 adds link cards), the same `upgrade` and the same normalization: the stored document is `{...document, boardId: <import id>, title}` and the canonical size is checked on it); **with `import`** the document may hold images, videos and (v16) link cards with thumbnails, each thumbnail staged as a picture; then the sequence below | 201 with the board's details, as today; 410, 403, 409 `import_in_progress`, 400 `asset_missing`. **Without `import`** a document holding an object that names media (an image, a video or, v16, a card with a non-null `asset`) is still 400 `images_not_supported`; cards with `asset: null` are accepted, and the whole route is word for word API v14 |

**Finish sequence** (with `import`):
1. `token = room(import).claimImport(person, workspace, document)`; a refusal is the answer, nothing else happens.
2. The board row: `create_board(workspace, person, title, board := import)` ([hosted persistence v13](0003-hosted-persistence-v13.md)),
   which re-checks the person's workspace membership and role inside the insert. A refusal that confirms no row was
   written by this call (`not_found` 404 for an absent or disabled member; `role_too_low` 403 with `needed: "editor"`
   for a viewer or guest; `board_exists` → 409 `import_in_progress`) calls `releaseImport(token)` (best effort) and is
   the answer, with **no clean-up**.
3. **Amendment A4 (2026-11-25).** For any other failure of step 2 (a lost reply, the server's RPC timeout, 503),
   the outcome is unknown. The claim excludes another finish, so the route first awaits
   `discard_import(board, workspace)` ([hosted persistence v13](0003-hosted-persistence-v13.md)). It tombstones the
   id and deletes any row with it, so an insert still in flight can never commit afterwards. Only after SQL cleanup
   succeeds does the route call `removeRoom(import)`. If SQL cleanup fails, the room stays importing and gated with
   its claim and `finishing` mark, so A1 expiry retries SQL cleanup before erasing it. If room removal fails after
   SQL cleanup, the tombstone already protects the id and staging expiry handles the remaining room. Either cleanup
   failure answers 503 `creation_cleanup_failed`. Successful cleanup answers 503 `service_unavailable`.
4. `room(import).create(document, person, token)`. Any failure runs the same ordered compensation in A4. If cleanup
   succeeds, the route rethrows 409 `room_exists` or 410 `upload_expired` when applicable and answers 503
   `service_unavailable` for other failures. A cleanup failure answers 503 `creation_cleanup_failed`.

**Amendment A1 (2026-11-25).** If the server stops during a claimed finish, [staging expiry](0003-hosted-storage-v15.md#staging-deadlines-both-kinds)
runs `discard_import` before the runner erases the room.

The board is visible to the workspace from the moment its row commits in step 2, after every file it names is held,
and its room holds the document before the route answers (the same window as today's create). S142's lost-reply
behaviour stays for creates without `import`.

## Template uploads and assets

| Step | Route | Body (limit) | Checks, in order | Answers |
| --- | --- | --- | --- | --- |
| Open | `POST /workspaces/:workspace/template-uploads` | `{ "assets": <asset list> }` (1,048,576) | Workspace role as the import's Open; shape `["assets"]`; the asset list; the sum of all `bytes` ≤ **20,971,520**; then `templateMedia(<new id>).open` | **201** `{ "upload": "<upload id>" }`. 400 `bad_request`; 413 `template_too_large` |
| Upload | `PUT /workspaces/:workspace/template-uploads/:upload/assets/:hash` | Raw bytes, read **whole** after `begin`, at most 20,971,520 (413 `body_too_large` beyond) | Ids; workspace role; `token = begin` (410, 403, 409 `upload_in_progress`, 400); the head classified as API v14 (a picture: `pictureHeader`, longer side at most 4,096, else 400 `unsupported_picture` / `picture_too_large`; a video: `videoType` with no picture signature; neither: 400 `unsupported_picture`); SHA-256 equal to `:hash` (else 400 `picture_hash_mismatch`); `stage` (the entry's type and bytes); `end(…, token)` in a `finally` on an early failure | **201** `{ asset, type, bytes }`, or **200** if held |
| Read | `GET /workspaces/:workspace/templates/:template/assets/:hash` | — | `get_template` (the existing SQL rights: owners, editors and viewers of the workspace; a guest 403 `role_too_low`; others 404); its `store` holds `:hash` | **200** the bytes with `Content-Type` the stored type, `Content-Length`, `Cache-Control: private, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff`. 404 `not_found` for an unknown template, a template without a store or a hash it does not hold |

**Saving and replacing** (the existing routes, changed):
- `POST /workspaces/:workspace/templates` accepts today's shape `["name","description","sourceBoard","objects"]` or the
  same plus `"upload"`. `PATCH /workspaces/:workspace/templates/:template` accepts `{sourceBoard, objects}` (today's)
  or `{sourceBoard, objects, upload}`; `{name, description}` is unchanged. `upload` must be an upload id (400).
- **Without `upload`**, `templateObjects(value)` refuses any object that names media (an image, a video or, v16, a
  card with a non-null `asset`) with 400 `bad_request`, exactly as today; a card with `asset: null` is accepted. A
  replace without `upload` (a media-free selection) stores `store = null`.
- **With `upload`**, in this order: when no object names media (no image, no video and, v16, no card with a non-null `asset`), 400 `bad_request` before anything else
  (the staging is not consumed and expires on its own); `held = templateMedia(upload).commit(person, workspace)` (410,
  403; one use: a committed store answers 410 and is not discarded);
  `templateObjects(value, held)`, which accepts images, videos and (v16) link cards whose media hashes are all in `held`
  with their kinds, a card's thumbnail as a picture (else 400 `asset_missing`); an upload whose only media is card
  thumbnails is valid ([team templates v4](0008-team-templates-v4.md)); every other check unchanged (1–250 objects,
  262,144 bytes) except the wrapper, now version 16 (v16; it was version 15); on
  its refusal `removeTemplateMedia(upload)` and the refusal. Then the SQL save or replace with `store := upload`.
- **After the SQL call:** a confirmed refusal (the mapped `not_found` 404, `bad_request` 400, `template_limit` 409,
  `role_too_low` 403) runs `removeTemplateMedia(upload)` and answers as today. An unknown outcome (503, a lost reply)
  answers 503 and removes nothing (the row may name the store). On success of a replace, `removeTemplateMedia(<previous
  store>)` when the SQL answer names one (any replace, with or without `upload`). A failed removal is logged and does
  not change the answer.
- `DELETE /workspaces/:workspace/templates/:template` deletes the row as today and then removes the store the SQL
  answer names, if any; 204 as today.
- `GET /workspaces/:workspace/templates/:template` (the detail) answers today's keys plus **`"media"`**: the store's
  inventory (asset entries sorted by hash), `[]` for a template without a store or whose store is lost. The list
  `GET`, the `POST` and `PATCH` answers keep exactly today's keys (no `media`, no `store`).

## Link previews (v16)

New in v16. Both routes live in a new file, `apps/server/src/routes/link-preview.ts`, and call `runtime.linkPreview`
(the fetcher of [link preview v1](0012-link-preview-v1.md) bound to the runner's transport, clock and `LinkLimits`).
Neither touches a room, a template store or the database beyond the team route's role read.

**Registration in `apps/server/src/app.ts`.**
- **The public path branch.** `publicLinkPreview(runtime)` is registered with `app.use("*", …)` **after `app.onError`
  and before the existing first middleware**. When `c.req.path` is exactly `/link-preview` (Hono's strict path: no
  trailing slash, no other letter case; a query string does not change the path) it answers the request itself and
  never calls `next()`, so the existing middleware, its bearer read and its `allowedOrigin` `OPTIONS` short circuit
  never see that path. For every other path it only calls `next()`.
- **The existing first middleware is unchanged**, word for word, for every other path: its `allowedOrigin` CORS
  headers, its `OPTIONS` short circuit for `allowedOrigin` and its bearer read with the join and `/operator/`
  exceptions. `/link-preview/`, `/link-preview/x`, `/LINK-PREVIEW` and every other near match are not the exact path,
  so they take this middleware and need a bearer token like any route.
- **The team route.** `linkPreviewRoutes(app, runtime)` registers `POST /boards/:board/link-preview` **after
  `templateMediaRoutes`**, behind the existing middleware and the existing `/boards/:board/*` lifecycle gate.

### Routes

| Route | Who | Checks, in order | Answers |
| --- | --- | --- | --- |
| `POST /boards/:board/link-preview` | A signed-in owner or editor of the board | The existing bearer middleware (401 without a valid `Authorization`); the existing `/boards/:board/*` lifecycle gate (`active()`: a board that is not active is 404 `not_found`); the board id (404); `authorize(runtime, person, board, "board", "editor")` (non-member 404 `not_found`, viewer 403 `role_too_low` with `needed: "editor"`); the content type; the body; `LinkLimits` key `person:<person id>:<board id>`; the fetcher | The matrix below |
| `POST /link-preview` | Anyone, from a listed browser origin | The request's `Origin` header equals one entry of `runtime.linkPreviewOrigins` exactly (else 404 `not_found`, also when the list is empty or the header is absent or `null`); the method; **no `Authorization` is read** (one sent is ignored); the content type; the body; `LinkLimits` key `address:<client address>`; the fetcher | The matrix below |
| `OPTIONS /link-preview` | The CORS preflight | The `Origin` rule above (else 404 `not_found`) | **204**, with the CORS headers below |

Any other method on `/link-preview` from a listed origin is 404 `not_found`, with that origin's CORS headers. The
12,000 ms ceiling of link preview v1 section 10 starts as each route's handler starts, before the body is read. Every
phase's deadline (body, limiter, resolution, page, picture), its outcome on expiry and the rule that late results are
never used are that section's **deadlines table**; this contract does not restate them.

**Content type and body** (both routes): the request's `Content-Type` media type (before any `;`, compared
case-insensitively) must be `application/json`; a missing or different one is 400 `bad_request` before the body is
read. The body is then read by the routes' own **cancellable reader** (link preview v1 section 10), not the shared
`body()` of `routes/common.ts`, which stays unchanged for every other route. It keeps the shared reader's limit and
outcomes: more than 1,048,576 bytes is 413 `body_too_large`, as every JSON route; a body still arriving at the
request's ceiling is cancelled and answered 400 `bad_request`. The body must be exactly `{ "url": <string> }`
(`shape(input, ["url"])` and `typeof url === "string"`); anything else, unparsable JSON included, is 400
`bad_request`. The string itself is judged by the fetcher's address rules (a string that is not an acceptable
address is 422 `address_refused`, not 400). The server's own limit is **2,048** characters (F1; a longer string is
422 `address_refused`); the web app never sends an address whose serialized `href` is longer than **1,000**
([interaction v52](0001-interaction-v52.md)), so the server limit only judges other callers.

### Answers: the one status matrix

This is the only status table for the two routes; link preview v1 refers to it.

| Status | Body | When |
| --- | --- | --- |
| **200** | `{ "url": string, "title": string, "description": string, "site": string, "picture": { "type": string, "bytes": string } \| null }` | The page gave a title (a page larger than 1 MiB whose title lies within the first 1,048,576 bytes read included). `picture.type` is `image/png`, `image/jpeg`, `image/gif` or `image/webp`; `picture.bytes` is the picture's bytes in standard, padded base64. `picture` is `null` when the page named none or **any** picture step failed, including a picture address (`og:image`, `og:image:secure_url` or `twitter:image`) that does not parse against the page's URL, and a picture address or picture redirect target that parses but fails the address rules (F1, F2) or the address policy (no connection is made to it). `Cache-Control: no-store` |
| 400 | `bad_request` | The `Content-Type` is missing or not `application/json`; the body is not JSON, or not exactly `{ "url": <string> }`; the body was still arriving at the request's 12,000 ms ceiling (the reader is cancelled) |
| 401 | The existing bearer reasons (`token_missing`, `token_malformed`, …) | Team route only: no valid `Authorization` |
| 403 | `role_too_low`, `needed: "editor"` | Team route only: a viewer of the board (as [access v17](0003-access-v17.md)) |
| 404 | `not_found` | Team route: not a member, a malformed board id, or the board not active (the existing gate). Public route: the `Origin` is absent, `null` or not listed, the list is empty, or the method is neither `POST` nor `OPTIONS` |
| 413 | `body_too_large` | The body passes the shared reader's 1,048,576 bytes |
| 422 | `address_refused` | The pasted address fails the address rules (F1, F2); a page redirect `Location` **parses** but its target fails the address rules (a scheme other than `http` or `https`, a port other than 80 or 443, credentials, an IP literal, a refused name); or any **page** hop (the pasted address or a page redirect target) has an answer refused by the address policy, the operator's deny prefixes included (link preview v1, sections 2 and 3) |
| 422 | `preview_unavailable` | The page phase or the request's ceiling ran out after the body was read; the final page status is not 2xx; the page is not HTML or has an unusable `Content-Encoding`; a 3xx has a missing or unparsable `Location`, or is not 301, 302, 303, 307 or 308; more than 3 redirects; the body read failed after the status; no title |
| 429 | `rate_limited` | Over the route's limit (team: 20 a minute per person and board; public: 10 a minute and 200 a day per client address) |
| 502 | `preview_failed` | The fetch could not reach a status: no DNS answer for the name, a resolver failure (link preview v1 section 4), or a connection or TLS failure before any reply status |
| 503 | `service_unavailable` | The rate-limit store could not be reached, its call failed, or it did not answer within 1,000 ms (or by the ceiling, if earlier); nothing is fetched, and a late answer is ignored (a count it made may stand) |

Every error body has the existing shape `{ "error": { "reason": "<reason>" } }` (plus `needed` for 403). **The
browser maps any non-200 answer to a link-only card**, with no message. The rate limit is counted after the content
type and body checks and before the fetcher, so a refused address counts; a 429 adds no count.

New reason codes: **`address_refused`** (422), **`preview_unavailable`** (422), **`preview_failed`** (502) and
**`rate_limited`** (429).

### Bearer exemptions

The existing first middleware's exemptions are unchanged: the socket join `GET /boards/:board/join` (a ticket) and
paths starting with `/operator/` (the operator key). The exact path `/link-preview` is not an exemption added to that
middleware: the public path branch answers it before the middleware runs, so no bearer token is read there. No other
path becomes public: a request without `Authorization` to any other route, `/workspaces` and every near match of
`/link-preview` included, is 401 as before.

### CORS

| Path | Origins answered | `Access-Control-Allow-Methods` (preflight) | `Access-Control-Allow-Headers` (preflight) |
| --- | --- | --- | --- |
| Exactly `/link-preview` (the branch) | Only an `Origin` equal to an entry of `runtime.linkPreviewOrigins` (`allowedOrigin` is **not** answered there unless it is also listed) | `POST, OPTIONS` | `Content-Type` |
| Every other path (the existing middleware) | Only `runtime.allowedOrigin`, exactly as v15 | `GET, POST, PUT, PATCH, DELETE, OPTIONS` (unchanged) | `Authorization, Content-Type` (unchanged) |

On `/link-preview`, a listed origin gets `Access-Control-Allow-Origin: <that origin>` and `Vary: Origin` on the
preflight and on **every** answer: 200 and every error alike (400, 404 for a wrong method, 413, 422, 429, 502, 503).
The branch therefore catches its own errors and builds the error answer itself, with the same status mapping as
`app.onError` (a `RoomError` keeps its status and reason; anything else is 503 `service_unavailable`), instead of
leaving them to `app.onError`. No `Access-Control-Allow-Credentials` is sent. An unlisted, absent or `null` origin
gets no CORS header and 404. `linkPreviewOrigins` never adds a CORS header on any other path.

## Unchanged

The board asset routes, every other route and every other answer. A board create or import without `import` is word
for word API v14's, except that (v16) it accepts schema 13–16 and treats a card with a non-null `asset` as media
(`images_not_supported`). The two link preview routes above are the only new routes of v16, and the edits marked
(v16) the only changes to v15's routes; the existing first middleware (its bearer rule and its CORS) is word for word
v15's, and only the new public path branch, registered before it, answers the exact path `/link-preview`.
