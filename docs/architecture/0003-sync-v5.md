# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v5 (2026-11-03)

Status: Draft for 0004-W2 v1. When accepted it replaces [sync v4](0003-sync-v4.md) for later
work. Every rule, message, limit and close code of v4 still applies, word for word, except where
this version changes it. It changes three things:

- `joined` carries the room's **restore generation** ("Joining").
- The shared client **keeps the edits a dropped connection left unanswered and sends them
  again**, in order, with their own request IDs, after it rejoins. It does this only when the
  rejoin shows the same restore generation, the same epoch and a role that can edit ("Recovering
  after an interruption").
- The shared client notices a silent connection with a **ten-second progress deadline** on its
  edits ("The progress deadline").

The room changes only by the new `joined` field; nothing else in the room's handling, its
storage or its limits changes. The room's storage is in the
[hosted persistence contract](0003-hosted-persistence-v3.md), and who may do what is in the
[access contract](0003-access-v4.md). What the web app shows is in
[hosted storage v4](0003-hosted-storage-v4.md).

## Joining

v4's section applies. In addition, `joined` carries `restoreGeneration`: an integer, the room's
accepted `meta.restore_generation` ([hosted persistence v3](0003-hosted-persistence-v3.md),
"Restores and the restore fence") when it sends `joined`. It is 0 for a board that was never
restored. Both runners send it through the one shared room implementation
(`packages/board-room/src/room.ts`).

`restoreGeneration` changes when, and only when, the room accepts a restore. A client compares
it with the value in its own previous `joined` for **equality only**. It never compares it with
the fence or with the operator restore route's reply: on the Node runner a logical restore can
leave the accepted value greater than the generation that route returned, because the room
raises the fence again when it starts. Ordinary wakes, evictions and restarts without a restore
leave it unchanged.

## Waiting edits

v4's section applies. Its last paragraph is replaced:

Waiting edits and their deadlines survive the room being evicted from memory. When a connection
closes, or the Node server restarts and its connections drop, that connection's waiting edits are
deleted; the client rejoins and receives `joined`. The shared client then sends again what was not
`saved`, as "Recovering after an interruption" says. An edit the room had saved before its answer
was lost is answered from its receipt ("Retrying") and changes nothing.

## The shared client

v4's section applies, except for the items below, which replace or add to it.

- **Requests.** Each request is tracked as `sent`, `received`, `waiting`, `saved`, `refused` or
  `dropped`. A request keeps, in the open tab's memory only, its request ID, the exact base64
  update it sent, its group (if any, from `edit(board, group?)`), and the `id` and `generation`
  of every object the edit added or changed. Requests stay in the order they were made. Nothing
  is written to disk. The group never reaches the wire, as in v4.
- **Outstanding and final.** A request `sent`, `received` or `waiting` is **outstanding**; `saved`,
  `refused` and `dropped` are **final**. A final request never changes again: its state and reason
  stay as they are, and a later answer for it (a late `saved`, `received` or `refused`) is
  ignored. Every rule below that drops requests drops only outstanding ones.
- **One session per open board.** The session object (`BoardSession`) lives as long as the board
  is open in the tab. A rejoin opens a new connection for the same session; it does not make a new
  session. `close()` ends the session: every outstanding request becomes `dropped` with reason
  `session_ended`, and nothing is sent again.
- **Ending an attempt.** A connection attempt ends when the transport closes with any code, when
  sending on it throws, when the progress deadline expires, or when the caller calls
  `interrupt()`. Then every request `sent` or `received` becomes `waiting`, its deadline is
  cancelled, presence is cleared, and the connection (if still open) is closed with code 1000.
  From then on every message, close or error from that attempt's transport is ignored. Each
  ending is reported once:
  - a close by the transport is reported as `{ kind: "close", code }` with its code, as in v4
    (the room's 1012, 1013, 4401, 4403, 4409 and 4423 included);
  - a send that throws is reported as `{ kind: "close", code: 1006 }`;
  - the progress deadline is reported as "The progress deadline" says;
  - `interrupt()` reports nothing (the caller knows).

  The client does not rejoin by itself after any of these. The caller rejoins with
  `reconnect()`, which ends the current attempt (if any) and joins again with a new ticket. The one
  exception is v4's rejoin after a refusal ("Refusals" below): the client rejoins by itself, and
  the close of the old transport that this rejoin makes is not reported.
- **Undo after a rejoin.** Every `joined` after the first clears the session's undo and redo steps
  (v4, "Undo on a shared board"). After a rejoin, the tab cannot tell its own unanswered edit,
  which the room saved under an assignment the tab never saw, from someone else's later edit to
  the same value. Keeping the steps could therefore undo another person's work.
- **A fresh Yjs client ID.** The first `joined` may use the client ID the caller gives
  (`clientId`, for tests). The document built from every later `joined` uses a new random Yjs
  client ID, so that no clock this tab used before the drop is used again. Waiting updates keep
  their original IDs and clocks.
- **Refusals.** v4's "A refused edit" applies, with reasons attached to the requests it makes
  `dropped`. A refusal with `epoch_changed` or `role_too_low` makes the refused request
  `refused` and every other request not yet `saved` `dropped` with reason `access_changed`.
  Any other refusal makes them `dropped` with reason `refused_edit`. "Every other request" means
  every other outstanding request.
- **Resync.** v4's rule is unchanged and is separate from recovery: on `resync`, every request
  `received` becomes `dropped`, and their content goes in one new combined request.
- **Closing.** v4's "Closing" item is replaced by "Ending an attempt" above and "Recovering after
  an interruption" below.

## Recovering after an interruption

When `joined` arrives after an earlier `joined` on the same session, the client compares it with
the session's last accepted `restoreGeneration`, `epoch` and role, before it applies any waiting
update:

1. **A different `restoreGeneration`.** The board was restored. Every `waiting` request becomes
   `dropped` with reason `board_restored`, and nothing is sent again. This takes precedence over
   2.
2. **A different `epoch`, or the role `viewer`.** Every `waiting` request becomes `dropped` with
   reason `access_changed`, and nothing is sent again. Any epoch change counts, a raise included:
   an edit made under the old epoch never applies under a new one ([access v4](0003-access-v4.md),
   "Epoch").
3. **Otherwise** (same restore generation and epoch, role `editor` or `owner`), the client:
   1. takes the room's board from `joined`;
   2. marks a `waiting` request **not kept** when an object it added or changed is not on the
      room's board and that object's generation is in the room's `retiredGenerations` (someone
      deleted it). Such a request is still sent and saved (v4, "Two people, one board", rule 4:
      the delete wins), and is counted once however many of its objects were deleted. An object
      the request added that is simply absent, with its generation not retired, is not "deleted";
   3. applies each `waiting` update to that board, in the original order, so the person's work
      stays on screen;
   4. sends the `waiting` requests again, **one at a time, in their original order**, each with
      its original request ID and its original update bytes. It sends the next one only after
      the previous one is answered `saved`. A `received` does not advance the queue. While any
      request is being sent again, the client refuses new edits, undo and redo with
      `join_required`, so new work cannot overtake older work;
   5. when the last one is `saved`, reports `{ kind: "recovered", requests }` with the number of
      requests it sent again. It reports `recovered` only when it sent at least one.

The session is **recovering** from the moment it applies a `joined` that leaves at least one
`waiting` request to send again (case 3) until it reports `recovered`, or until the attempt ends,
`discard()` or `close()` is called, or a refusal drops the rest. While it is not recovering, its
edits follow the role as in v4. A rejoin under case 1 or 2, or with nothing waiting, leaves it not
recovering: editing follows the role at once. The session exposes this as `recovering`.

A request sent again is an ordinary edit: the room answers it from its receipt when it had saved
it before the answer was lost ("Retrying"), saves it otherwise, or refuses it. A refusal is handled
by "Refusals" above.

The caller may end the waiting work at any time with `discard(reason)`. Every outstanding request
then becomes `dropped` with that reason, the undo and redo steps are cleared, the current attempt
ends as `interrupt()` ends it (reporting nothing), and the client reports
`{ kind: "discarded", reason }`. The session's document may still hold the discarded changes, so
until a later `reconnect()` brings a new `joined` (whose board replaces the document), edits, undo
and redo are refused with `join_required`. The web app uses `discard()` for a board it can no
longer open, or an account that can no longer open boards (`access_removed`), a sign-out
(`signed_out`) and a sign-in that cannot be renewed (`sign_in_expired`)
([hosted storage v4](0003-hosted-storage-v4.md)); in each case the board then ends.

## The progress deadline

Each time the client sends a request (the first time or again), it starts a **ten-second** timer
for it. `received` for that request restarts its timer. `saved`, a refusal, `dropped` and the end
of the attempt cancel it. When a timer expires, the client first ends the attempt as "Ending an
attempt" says, so that no later message on the old connection can change a request, and then
reports `{ kind: "close", code: 4000, reason: "answer_deadline" }`. Code 4000 is the client's own
report. It is never sent on the wire and never seen as a WebSocket close code; the connection
itself is closed with 1000.

Ten seconds is shorter than the room's 30-second limit for an incomplete edit ("Waiting edits"),
so a slow but valid edit can be cut off. The client then rejoins and sends it again, and the
receipt keeps it from being saved twice. The deadline does not apply to joining (the caller's own
15-second limit does) or to presence.

## Close codes

v4's table applies. The client's own deadline report (code 4000, above) is not in it.

## Not in this version

Editing while disconnected; keeping waiting work across a reload, a tab close or on disk;
sending waiting work again across a restore, an access change, a sign-out or a sign-in that
cannot be renewed; keeping undo across a rejoin; recovering the requests that a `resync` drops; a
protocol ping; hosted pictures; and version history or conflict review.
