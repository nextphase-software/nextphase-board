# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v14 (2026-11-16)

Status: Draft for 0010-W3 v1. Replaces [sync v13](0003-sync-v13.md), whose document, comment, timer,
vote, spotlight, renew, presence, reaction and close rules remain in force word for word except as below.
[Document v19](0001-document-v19.md) lets a hosted board hold several pages. This version:
- changes how pages live in the shared document, so that several people can change pages at the same
  time without losing a change;
- says what hosted Undo does with pages;
- adds the sender to the `update` frame;
- names the origin of each board change a client applies.

The presence frame's new `page` key is owned by [presence v5](0004-presence-v5.md).

## Pages in the shared document

The board map's `pages` value (one whole array, sync v13 through document v18) is replaced by the board
map key **`pageMap`**. `pageMap` is a shared map keyed by page id. Each entry is a shared map with exactly
two keys:

| Key | Value |
| --- | --- |
| `name` | The page's name (document v18's rules) |
| `order` | The page's **order key** (below) |

The codec's allowed board-map keys become `schemaVersion`, `boardId`, `title` and `pageMap`. One more key
is tolerated: **`pages` only as a deleted entry** (the tombstone that conversion leaves, below). It is
never read. The codec refuses, with its existing `invalid_update` reason:
- a live `pages` value;
- any other key;
- a `pageMap` entry that is not a shared map with exactly `name` and `order`;
- an entry key that is not a lowercase UUID;
- an invalid order key;
- a name that is not a string.

### Order keys

An **order key** is a string of 1 to 64 characters from the 62-character alphabet `0`–`9`, `A`–`Z`,
`a`–`z` (in that code-unit order), whose **last character is not `0`**. Keys compare as strings by UTF-16
code unit. Between any two different valid keys there is always another valid key, and below or above any
valid key there is always one.

`order-keys.ts` holds one pure, deterministic function `between(low, high)`:
- `low` is a key or absent (no lower bound); `high` is a key or absent (no upper bound);
- it returns the shortest valid key strictly between them;
- among equally short keys it returns the one nearest the midpoint, rounding down;
- it returns **none** when `low` and `high` are equal, or when the result would exceed 64 characters.

A **rebalance** gives the pages, in their order, the keys `between` produces when called in turn on an
empty range: the first page gets `between(absent, absent)` and each next page `between(previous key,
absent)`. The keys are therefore deterministic for a given page count.

### Reading

The board's `pages` array is the entries sorted by `order`, with ties broken by page id (both compared
by code unit). Each page is `{id, name}` in that order. Document v18's rules then apply to the board as
read, so an empty `pageMap`, more than 50 entries or an invalid name fail `validate` as before.

### Writing

The adapter's `set` receives the next whole board and, from a page step, the **moved pages**: the ids of
the pages whose place that step changed. For Move up and Move down this is the moved page; for a drag,
the dragged page; for Add page and Duplicate page, the new page. Other edits pass none. The page step
hands them through the existing commit seam to the hosted session's edit as an optional argument. Inside
one transaction:
1. Delete the entries of pages no longer in `pages`.
2. Add an entry for each new page.
3. Set `name` only where it differs from the stored name.
4. If the next board's page order equals the order read from the (updated) entries, write no `order`.
   Equal keys from concurrent adds therefore never cause a write by themselves.
5. Otherwise, if moved pages were given and the stored keys of **all other pages** still strictly
   increase in the new order, those pages keep their keys. If not, or if none were given, take the stored
   keys in the new page order and find the **longest strictly increasing subsequence** of them (pages
   without a key take no part). When several have the same length, choose the one whose list of positions
   is first in lexicographic order. Those pages keep their keys.
6. Every other page, from first to last, gets `between(key of the nearest earlier page that has a kept
   or newly given key, or absent; key of the nearest later page with a kept key, or absent)`.
7. If any `between` call returns none, rebalance every page instead.

So, except for a rebalance, a rename writes one `name`, a move writes only the moved page's `order`, an add
writes one entry and a delete removes one. Nothing else in `pageMap` is written.

### Concurrent changes

The room's arrival-order rule (`promote()`, sync v9 onward) is extended to the `name` and `order` writes
inside `pageMap` entries, exactly as it applies today to the keys of object maps. A write into an entry
that has been deleted is skipped, as a write into a deleted object is. Adding or deleting an entry is not
promoted: different page ids never collide. Changes then merge like this:
- different pages: both changes are kept;
- the same page's name, or its order key: the later arrival wins;
- a delete and a rename (or move) of the same page: the delete wins. The rename or move is discarded
  with the deleted entry, the edit carrying it is still accepted, and nothing recreates the entry;
- two pages added at once between the same neighbours may get equal keys; reading orders them by id.

An edit whose result leaves an object on a page that no longer exists is refused `invalid_document`
(document v19). The client's existing refused-save recovery reloads the room's board, and the objects
that edit added are not kept. No new refusal reason or recovery path is added.

### Stored rooms and backups

A room whose stored shared document holds the old live `pages` value converts it **in place** when it
loads ([hosted storage v12](0003-hosted-storage-v12.md)):
- It reads the board with the **legacy reading**: sync v13's codec rules, where a live `pages` value is
  the array. This reading is used only by this conversion and by restoring a storage-version-7 backup;
  client updates never get it.
- It then, in one shared-document transaction, writes `pageMap` with one entry per page (keys from a
  rebalance) and deletes `pages`, leaving the tombstone the codec tolerates.

This is not a person's edit: no edits row, receipt, revision or history version. The room writes the
snapshot at the current revision, so a reload reads the converted document. A client that held the old
document receives the conversion as an ordinary update on its next join or resync. Restoring a
storage-version-7 backup runs the same legacy reading and conversion before the restored board is
validated.

## Undo on hosted boards

`pageMap` entries are handled by the hosted Undo units (sync v6 onward) exactly as object maps are:
- each entry is a unit `page:<page id>`;
- each of its keys (`name`, `order`) is a value with **its own item identity**, used as the guard;
- adding or deleting the entry is a whole-unit change, guarded by the identities of its keys.

Steps record and undo page changes like this:
- **Add page:** one step; its Undo deletes the entry (and the page's objects if the step created any).
- **Delete page:** one step together with the deletion of its objects. Its Undo adds the entry back with
  its id, name and order key. It re-creates the objects as hosted Undo re-creates deleted objects today:
  with **fresh ids and generations** and the same content, positions, page and references remapped to
  the new ids (`undo.ts`, identity registration in `edits.ts`; unchanged).
- **Rename or move:** one step on the changed values.
- **Move to page:** one step on the moved objects' `page` and on the connectors it deleted.

The guard rules are unchanged. If someone else has since written a value a step would change (a
same-value write counts), that part is not undone, and the existing words "Someone else changed that, so
it was not undone." apply. Undo and Redo report the page that was open when the step was made, as local
Undo does ([interaction v44](0001-interaction-v44.md)).

## The `update` frame names its sender

The room's `update` frame to other connections gains **`connection`**: the sender's presence connection
id (lowercase UUID), the same id `present` frames carry. The frame is exactly
`{kind: "update", revision, update, connection}`. `saved`, `resync` and the join frames are unchanged.
The client uses `connection` only to name the person in interaction v44's remote-delete notice, through
the presence list. An unknown connection reads `Someone`.

## Change origins on the client

The hosted session reports each board change it applies with exactly one **origin**:

| Origin | When |
| --- | --- |
| `own` | This tab's commit, Undo or Redo |
| `remote` | An `update` frame, with its `connection` |
| `reload` | Join, resync, refused-save recovery, document restore (4423), entering or leaving a history preview |

[Interaction v44](0001-interaction-v44.md)'s remote-delete notice applies only to `remote` changes.

## Presence, comments and votes

The presence frame gains `page` ([presence v5](0004-presence-v5.md)). The comment anchor gains `page`
([comments v5](0005-comments-v5.md)). The vote `start` command gains `page`
([workshop voting v3](0007-workshop-voting-v3.md)). Each is validated where its contract says. None of
them is queued, replayed or retried differently from today.
