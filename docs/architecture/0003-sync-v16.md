# 0003 — Room sync contract

CONTRACT VERSION: 0003 sync v16 (2026-11-22)

Status: Draft for 0012-W3 v1. Replaces [sync v15](0003-sync-v15.md), whose rules remain in force word for
word except as below. [Document v20](0001-document-v20.md) is unchanged: the room's live board stays schema
version 14, and the image object keeps exactly its keys (`asset`, `pixelWidth`, `pixelHeight`,
`description`). This version lets a team board hold **image objects** once the room holds their pictures. In
sync v15's "The room" section, "The room's storage version stays **8**" and "Images are still refused as today"
are replaced: the storage version is **9** ([hosted storage v13](0003-hosted-storage-v13.md), read exactly as 8 is),
and images are accepted as below.

## Editing

Step 5 of the edit rules (sync v4, carried through v15) ends: "and it adds no image object … or
`images_not_supported`". That clause is replaced by:

> and **every image object that the edit adds, or whose `asset` it changes, refers to a picture the room
> holds** (hosted storage v13's held predicate). An image object whose id was on the board before the edit with
> the same `asset` is not checked. Otherwise the edit is `refused` with the reason **`asset_missing`**. Nothing is
> stored.

"Before the edit" is the board step 5 already compares against (its before/after rule). The check runs after every
other step-5 check, in `packages/board-room/src/edits.ts` where the image refusal is today, reading the room's
storage. Edits (also waiting edits retried later), picture stores, captures and clean-up all run one at a time in
the room's ordered queue (`Room.ordered()`), so no picture can be stored or removed between this check and the
edit's write. `images_not_supported` is no longer sent by the room. The board rename path reuses `evaluate()`; it
changes no image, so it is never refused for a picture.

So a board that holds an image whose picture is missing (for example after a version restore, below) still takes
every other edit, rename, deletion of that image, Duplicate of other objects and Undo or Redo of other steps.
What is refused is adding such an image again: a Duplicate, Paste, Undo or Redo that re-adds an image whose picture
the room no longer holds.

A client sends an edit that adds an image only after the picture's upload to this board answered 200 or 201
([API v13](0003-api-v13.md)), or for an image copied (Paste, Duplicate) or restored (Undo, Redo) on the same board
whose picture the tab holds ([interaction v49](0001-interaction-v49.md)). Uploading a picture the room already holds
is allowed and stores nothing new (200). An `asset_missing` refusal takes the existing refused-edit path in
`packages/board-sync/src/session.ts` (the request is marked refused, the session drops with `refused_edit` and
rejoins), with no new client handling.

## Undo, Redo and history

Hosted Undo and Redo (sync v15 and earlier) restore image objects as they restore any object: the step holds
the object's document keys, never picture bytes, and no upload is made. Pictures stay held while a version, the
live board or a recent upload refers to them ([hosted persistence v11](0003-hosted-persistence-v11.md)), so an
Undo or Redo of an image normally finds its picture. If it does not (the picture was removed because no version,
the live board or an upload of the last 24 hours referred to it), the step is refused with `asset_missing` through
the path above. The same holds for a paste of a picture the tab holds that the room has removed since.

Version previews, version restore and the history list read images like any other object: the room's version and
restore paths no longer refuse a document holding an image (`packages/board-room/src/history.ts`, the two image
refusals). A version restore is never refused for a picture the room does not hold; such an image shows the web
app's missing-picture box ([interaction v49](0001-interaction-v49.md)) and is not checked by later edits that leave
it as it is.

## The codec

The sync adapter already reads and writes the image object's keys
(`packages/board-sync/src/document-adapter.ts`); it does not change. No frame, presence key, comment, vote or
timer rule changes. Pictures never travel in a socket frame: the 1 MiB message limit and the 2 MiB stored
document limit are unchanged, and an image object adds only its document keys to them.
