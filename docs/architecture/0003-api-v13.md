# 0003 — Server API contract

CONTRACT VERSION: 0003 API v13 (2026-11-22)

Status: Draft for 0012-W3 v1. Replaces [API v12](0003-api-v12.md), whose routes, authentication, origins,
tickets, capacity, lifecycle ordering, socket rules, template routes and error bodies remain word for word
except as below. This version adds the two **picture routes** that store and serve a team board's pictures.
They are registered in `apps/server/src/app.ts` from a new `apps/server/src/routes/pictures.ts`, so the
Cloudflare Worker and the Node runner serve them identically. Where the pictures are kept is
[hosted storage v13](0003-hosted-storage-v13.md); who may use the routes is [access v14](0003-access-v14.md).

## Terms

- A **hash** is 64 lowercase hexadecimal characters: the SHA-256 digest of a picture's bytes, as
  [document v20](0001-document-v20.md)'s image `asset` key holds it.
- A **picture type** is read from the bytes' signature only (never the request's `Content-Type` or a name),
  exactly as the web app's `signature()` reads it: PNG (`89 50 4E 47 0D 0A 1A 0A`), JPEG (`FF D8 FF`), GIF
  (`GIF87a` or `GIF89a`), WebP (`RIFF`, any four bytes, `WEBP`). Their types are `image/png`, `image/jpeg`,
  `image/gif` and `image/webp`.
- A picture's **header size** is its width and height read from its header, never by decoding it:
  - PNG: the big-endian 32-bit width and height at byte offsets 16 and 20 (the first chunk must be `IHDR`
    at offset 12);
  - GIF: the little-endian 16-bit logical screen width and height at offsets 6 and 8;
  - JPEG: walk the markers from offset 2. At each position, skip any `FF` fill bytes before a marker byte; a byte
    other than `FF` where a marker must start makes the size unreadable. `FF 01` and `FF D0`–`FF D7` stand alone
    (no length). `FF D9` (end of image) or `FF DA` (start of scan) reached before a start-of-frame makes the size
    unreadable. Every other marker is followed by a big-endian 16-bit length of at least 2 that includes itself;
    a length below 2, or a segment that runs past the end of the bytes, makes the size unreadable. The first
    start-of-frame marker `FF Cn` with `n` from `0` to `F` except `4`, `8` and `C` gives the size: its
    big-endian 16-bit height at marker + 5 and width at marker + 7 (its length must be at least 8);
  - WebP: the chunk at offset 12. `VP8 ` (with a space): width `= u16le(26) & 0x3FFF`, height
    `= u16le(28) & 0x3FFF`. `VP8L`: byte 20 must be `0x2F`; with `b = u32le(21)`, width `= (b & 0x3FFF) + 1`,
    height `= ((b >> 14) & 0x3FFF) + 1`. `VP8X`: width `= u24le(24) + 1`, height `= u24le(27) + 1`.

  The header size is **unreadable** when the bytes end before a value is read, a required marker or chunk
  is missing, or either side is 0. The server never checks that the header size equals an image object's
  pixel size (a JPEG's orientation may swap them in the browser); it checks only the longer side.

## Routes

| Route | Body | Success | Refusals |
| --- | --- | --- | --- |
| `PUT /boards/:board/assets/:hash` | The picture's bytes, raw (any `Content-Type`; the web app sends `application/octet-stream`) | 201 `{asset, type, bytes}` when the picture was stored now; 200 with the same body when the board already held it (its upload time is renewed, [hosted persistence v11](0003-hosted-persistence-v11.md)) | 404 `not_found` (path, access, lifecycle); 403 `role_too_low`, `needed: "editor"` (a viewer); 413 `body_too_large` (over 20,971,520 bytes); 400 `unsupported_picture` (empty, no picture signature, or an unreadable header size); 400 `picture_too_large` (the header size's longer side above 4,096); 400 `picture_hash_mismatch` (the bytes' SHA-256 is not `:hash`); 409 `board_pictures_full`; 503 `service_unavailable` |
| `GET /boards/:board/assets/:hash` | — | 200, the picture's bytes exactly as stored, with `Content-Type` its picture type, `Content-Length`, `Cache-Control: private, max-age=31536000, immutable` and `X-Content-Type-Options: nosniff` | 404 `not_found` (path, access, lifecycle, or a picture the board does not hold); 503 `service_unavailable` |

`asset` is the hash, `type` the picture type and `bytes` the stored byte count.

**Checks run in this order** for both routes; the first that applies answers, before anything is written (except
the clean-up that a `board_pictures_full` refusal commits, hosted storage v13):

1. The existing bearer authentication (every route but `/join` and `/operator/*`, unchanged).
2. The existing lifecycle gate for `/boards/:board/*` (`app.ts` middleware, which runs before the route and only
   when `:board` is a UUID): a board that is not active is 404 `not_found`. The middleware's existing exceptions
   for paths ending `/trash`, `/lifecycle` or `/join` are unchanged; such a path never names a picture, because
   `trash`, `lifecycle` and `join` are not hashes. CORS preflights (`OPTIONS`) are answered by the existing CORS
   middleware before any of these checks, as for every route. For a board that is not active, a path ending
   `/join` (for example `/boards/<board>/assets/join`) answers as the middleware does today (401 `ticket_invalid`);
   such a path never names a picture.
3. Path values, in the route: `:board` a lowercase UUID (`id()` in `routes/common.ts`) and `:hash` a hash (a new
   validator beside it); otherwise 404 `not_found`.
4. Access, through the existing `authorize()` for the board: no role is 404 `not_found`; for `PUT` only,
   `needed: "editor"` (a viewer is 403 `role_too_low`; owners, editors and guests with an editor grant pass,
   as `authorize()` answers today). `GET` needs any role.
5. `PUT` only, the body: read as raw bytes by a new `bytes(c, limit)` in `routes/common.ts` that streams the
   request body exactly as `body()` does and cancels with 413 `body_too_large` once it passes the limit
   (20,971,520), but never parses it. Then, in this order: `unsupported_picture`, `picture_too_large`,
   `picture_hash_mismatch` as the table says.
6. The board's room: `PUT` stores the picture and `GET` reads it, as hosted storage v13 says (admitted as the
   existing export call is, with the caller's role looked up again inside the room, and its errors and their HTTP
   mapping). `PUT` answers 409 `board_pictures_full` when
   the board's held pictures (after the clean-up that hosted persistence v11 runs first) with this new one would
   exceed 52,428,800 bytes; a picture the board already holds is never refused by this check.

Any other storage or room failure is 503 `service_unavailable` and stores nothing of the picture. Error bodies use the existing
`errorBody` shape. Both routes send the same CORS headers as every other route (the allowed methods already
include `PUT`; the allowed request headers stay `Authorization, Content-Type`). Only these two routes carry the
caching headers above; no other route changes.

## Unchanged refusals

The board import route (`POST /workspaces/:workspace/boards`, 13 MiB body) still answers 400
`images_not_supported` for a document holding an image, and the template routes still refuse an `image` object
with 400 `bad_request` ([team templates v2](0008-team-templates-v2.md)). Bringing a board file or a template
with pictures into a team workspace is later work. No other route, socket frame, ticket or joined field
changes.
