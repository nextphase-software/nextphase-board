# 0003 — Server API contract

CONTRACT VERSION: 0003 API v2 (2026-10-30)

Status: Draft for 0003-W3 v1. It replaces [API v1](0003-api-v1.md), adding the lists of
workspaces and boards, recent boards, renaming, and an optional title on creation. It lists the
server's HTTP routes, their requests and replies. Who may call each route is in the
[access contract](0003-access-v2.md); token checks are in the
[identity contract](0003-identity-v1.md); the room connection opened by the join route is in the
[sync contract](0003-sync-v1.md); how a board's name and last-edited time reach the lists is in
the [hosted persistence contract](0003-hosted-persistence-v2.md).

## Common rules

- One application serves every route on both runners: a Cloudflare Worker and the Node
  server.
- Every route except the join upgrade and the operator routes needs
  `Authorization: Bearer <access token>`. The token is checked before anything else.
- IDs in paths are lower-case UUIDs; anything else is 404 `not_found`.
- Request and reply bodies are JSON (`Content-Type: application/json`). A request body over
  1 MiB (1,048,576 bytes) is refused with 413 `body_too_large`, except on the operator restore
  route, whose limit is 16 MiB (16,777,216 bytes), with the same refusal above it; a body that is not the stated
  shape is refused with 400 `bad_request`.
- Every refusal has the body `{ "error": { "reason": "<reason>" } }`, with `"needed"` added
  only to 403 `role_too_low` (see the access contract). Reasons are lower-case words joined by underscores and are
  part of this contract.
- An unknown route, an unsupported method, and every route for images, comments, deletion or
  removal is 404 `not_found`.
- Replies to a browser carry `Access-Control-Allow-Origin` only for the one origin named in
  the server's settings; preflight requests for that origin are answered with the methods and
  the `Authorization` and `Content-Type` headers below. The allowed methods are `GET`, `POST`,
  `PUT`, `PATCH` and `DELETE`.

## Boards

A title is 1 to 120 characters (Unicode code points), not only white space, with no unpaired
surrogate, as [document v10](0001-document-v10.md) requires of a board's `title`; any other
title, including `null`, is 400 `bad_request`. The routes that take a title (creation and
renaming) also refuse a title holding U+0000 with 400 `bad_request`, because the board's row
in Postgres cannot store that character; the document's own rule is unchanged (hosted
persistence contract, "Names and edited times in lists", says how such a title made by an
ordinary edit is copied). The creation body is a JSON object that is either
empty, giving the title `Untitled`, or holds only `title`; a missing body, any other key or a
body that is not an object is 400 `bad_request`. Creating a board writes its row in Supabase,
then answers. The board's room is created the
first time anything opens it (a join ticket, a join or an export), with an empty version 10
document whose `boardId` is the board's ID and whose `title` is the creation title. Creating
the room is idempotent, so a failure between the two steps leaves a board that sets itself up
when it is first opened.

While a board's room is locked after a restore ([hosted persistence
contract](0003-hosted-persistence-v2.md)), the routes that need the room (join tickets, join,
export and rename) answer 503 `room_locked`, or 503 `access_log_pruned`, to a person in the room's
copy of access, and 404 to anyone else, always before any WebSocket upgrade. Connections open
when a restore starts are closed with 4423 (sync contract). Board details come from Supabase and are not affected.

`title` in board details and in every list is the board's name as last copied from its saved
document (hosted persistence contract, "Names and edited times in lists"). It can lag the
document for a short time after a save, and for longer while Supabase is unreachable.

## Renaming

`PATCH /boards/:board` with `{ "title" }` (the title rule above; no other key) renames the board
by saving one edit to its document through the board's room: the same order of edits, document
rules, receipt and `update` broadcast as an edit sent over the room connection
([sync contract](0003-sync-v1.md)). The reply comes only after that edit is saved; its
`revision` is the board's revision after it. If the edit path refuses the edit, nothing is
saved, no receipt is kept and nothing is broadcast: a document that would exceed the size limit
is 413 `document_too_large`, and any other refusal of the sync contract's step 3 is 409 with
that refusal's reason. If the title equals the document's current title,
nothing is saved and the reply carries the current revision. The reply does not wait for the
lists: they show the new name once the room has copied it. A rename needs the room, so a locked
room answers as the other room routes do (below). A retried request is a new rename; there is no
idempotency key.

## Lists

**Workspaces.** `GET /workspaces` lists every workspace in which the caller is the owner, an
editor or a viewer, or a guest with a role on at least one of its boards, ordered by name (byte
order) then ID; `role` is the caller's workspace role. A guest with no board grant does not see
the workspace. A caller with no such workspace gets an empty list.

**A workspace's boards.** `GET /workspaces/:workspace/boards` lists the workspace's boards on
which the caller has a role, worked out when the page is read. A board row is `{ "id",
"workspaceId", "title", "role", "createdAt", "editedAt", "openedAt" }`: `role` is the caller's
role on the board, `editedAt` the time of the board's last saved edit as last copied (its
creation time until its first edit), and `openedAt` the caller's last open (below), or `null`.

| Query | Values | Default |
| --- | --- | --- |
| `sort` | `edited` (by `editedAt`), `created` (by `createdAt`), `title` | `edited` |
| `order` | `desc`, `asc` | `desc` |
| `cursor` | the `nextCursor` of the previous page | none (the first page) |

`title` order compares the title with the ASCII letters A–Z read as a–z, then the title itself,
both byte by byte (PostgreSQL `COLLATE "C"`); no language's collation is used. Every sort ends
with the board ID, so no two rows tie. A page holds at most 100 rows; `nextCursor` is `null` on
the last page. An unknown `sort` or `order` is 400 `bad_request`.

A cursor is an opaque string of at most 2,048 characters: base64url, without padding, of a
UTF-8 JSON object with exactly the keys `v` (the number 1), `workspace`, `sort`, `order` (as in
the request), `id` (the last row's board ID, a lower-case UUID) and `key`, a string holding the
last row's sort value:

| `sort` | `key` |
| --- | --- |
| `edited`, `created` | the time as PostgreSQL prints a `timestamptz` in UTC to the microsecond: `YYYY-MM-DD HH:MM:SS` followed by `.` and one to six digits when the fraction is not zero, then `+00` |
| `title` | the board's title, which must meet the title rule above |

The next page holds the rows that come after the cursor in the requested order: compared as the
tuple (time, ID) for the time sorts, and (title with A–Z read as a–z, title, ID) for `title`,
the first two parts worked out from `key`; `asc` takes greater tuples, `desc` smaller. It is not
signed and grants nothing: access is worked out again for every page. A cursor that does not
decode to that shape, whose `key` does not match its sort, or that was made for another
workspace, sort or order, is 400 `bad_request`. Walking the pages of a set of boards that does not change while it is walked
returns every board once. A board renamed, edited or created between two pages can appear twice
or not at all; clients that join pages remove repeats by ID.

**Recent boards.** `GET /recent-boards` lists the boards the caller opened most recently, at most
50, across all workspaces, newest first (ties by board ID, descending). A recent row is a board
row with `"workspaceName"` added. A board on which the caller no longer has a role is left out
before the 50 are counted. A caller who opened nothing gets an empty list.

**Opening.** A board counts as opened when the caller is issued a join ticket for it. The open is
recorded after the ticket is stored and does not delay or refuse the ticket; if recording fails,
that open is lost and the next ticket records again. An older open never replaces a newer one.

Export answers with `Content-Disposition: attachment; filename="board-<id>.json"` and the
document's canonical JSON as [document v11](0001-document-v11.md) defines it.

## Join tickets

A browser cannot set an `Authorization` header on a WebSocket, so the room is joined in two
steps:

1. `POST /boards/:board/join-tickets` with the token. The caller needs a role on the board.
   The reply's `ticket` is 32 random bytes in base64url (43 characters), valid for 30 seconds
   and for one connection.
2. `GET /boards/:board/join?ticket=<ticket>` as a WebSocket upgrade, within 30 seconds, from
   the allowed origin. The access token never appears in a URL.

A restore deletes every ticket, so after one a join with an earlier ticket gets 401
`ticket_invalid`; the 503 and 404 answers of a locked room come from the ticket and export
routes, which carry the person's token.

The room keeps only the SHA-256 digest of each ticket, with the person, the board, the
token's `exp` and the ticket's expiry, and deletes it when it is used or expires. A ticket
that is missing, unknown, expired, already used or issued for another board, or whose token's
`exp` has passed, gets 401 `ticket_invalid` before the upgrade. A request from another origin gets 403
`origin_not_allowed`. The connection then belongs to the ticket's person and lasts until the
token's `exp`, unless renewed (identity contract). The person's role is checked again when the
ticket is used, so a ticket never outlives a role.

## Invitations

An invitation reply is `{ "id", "workspaceId", "boardId", "email", "role", "expiresAt" }`.
The owner shares the invitation's ID as a link; the server sends no email.

When the invited email has no Supabase Auth account, the invite route creates one through the
Auth admin API, already confirmed, with no password and no email sent. The person signs in with
a one-time code that Supabase Auth sends to that address, so only whoever reads that mailbox can
use the account. The account must be created confirmed: with sign-ups switched off, Supabase
Auth treats signing in to an unconfirmed account as a new sign-up and refuses it. If
creating the account fails, the invitation is still recorded and the reply carries
`"accountCreated": false`; otherwise `true`.

Acceptance refusals: 404 `not_found` for an unknown invitation; 403 `invitation_email_mismatch`
when the signed-in email differs; 410 `invitation_expired`, `invitation_used` or
`invitation_cancelled`. Accepting is safe to retry: the person who accepted gets the same 200
reply again, with the offered role, even if their role has changed since.

## Raising roles

`PUT` on a member or a grant only raises. Setting the role a person already has is 200 and
writes nothing. A lower role is 409 `lowering_not_offered`. `owner` is never a value here
(400 `bad_request`). A `PUT` on a member who is not in the workspace is 404
`person_not_found`; a grant may be given to anyone already known to Board (a row in
`people`, identity contract), who becomes a `guest` if they are not a member; anyone else is 404
`person_not_found`.

## Operator routes

Operator routes are for the person running the server, not for people using boards. They need
the header `Board-Operator-Key` equal to the operator key in the server's settings (otherwise
401 `operator_key_invalid`), and are 404 when no key is set. They must be kept behind the deployment's own access control as well.

| Method and path | Body | Does |
| --- | --- | --- |
| `POST /operator/boards/:board/backup` | none | 200, a backup envelope ([hosted persistence contract](0003-hosted-persistence-v2.md)); 413 `backup_too_large` if it would exceed 16 MiB |
| `POST /operator/boards/:board/restore` | a backup envelope, up to 16 MiB | Raises the board's restore fence, closes the room's connections, replaces its storage with the backup, and answers 200 `{ "boardId", "restoreGeneration", "locked": true }` once the backup is stored and the room is locked; replay follows on the room's next request and the answer does not wait for it. 400 `bad_request` for an envelope of another format, version or board |
| `POST /operator/boards/:board/restore-to-time` | `{ "bookmark": string }` | Cloudflare only: raises the fence, closes the room's connections, schedules the restore and restarts the room, then answers 202 `{ "boardId", "restoreGeneration", "undoBookmark" }` (the bookmark `onNextSessionRestoreBookmark` returns, for undoing the restore); the restore takes effect when the room next starts; 404 on the Node server |
