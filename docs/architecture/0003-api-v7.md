## History routes

Bearer verification comes first (invalid authentication 401), then board ID/current access,
then permitted mutation role. Parse a valid request envelope; resolve accepted save/restore
receipts as described below before checking selected-version retention or the expected head.
New work then checks version ID/retention and query/body values. IDs are
lowercase UUIDs. Denied/missing board, malformed IDs and missing/expired versions use the
same 404 `not_found`, without title/name/author/count/document. A permitted viewer's mutation
gets 403 `role_too_low` before version probing. Unknown body/query keys or invalid types give
400 `bad_request`. Service/room failure gives 503 `service_unavailable`, never partial cached
success. History bodies retain the 1,048,576-byte ceiling and 413 `body_too_large`.

| Method/path | Exact query/body | Success |
| --- | --- | --- |
| `GET /boards/:board/versions` | None | 200 `{versions:[metadata],head:{revision,generation}}` |
| `GET /boards/:board/versions/:version` | None | 200 `{version:metadata,document}` |
| `POST /boards/:board/versions` | `{requestId,name,description}` | 200 `{version:metadata}` |
| `PATCH /boards/:board/versions/:version` | `{name,description}` | 200 `{version:metadata}` |
| `POST /boards/:board/versions/:version/restore` | `{requestId,expectedRevision,expectedGeneration}` | 200 `{requestId,revision,generation,beforeVersionId,restoredVersionId}` |

`metadata` has exactly lifecycle v1's keys. `document` is the validated canonical version-10
board. `head` is the live confirmed room head, never a historical revision. `requestId` is a
lowercase UUID chosen once by the client. Expected values are nonnegative safe integers.
Name/description are required string keys but may be empty; enforce lifecycle v1's 100/500
code-point/character rules. No client-supplied document, actor, capture time or board ID in bodies.
Preview responses can exceed the request limit within the 2 MiB canonical document ceiling;
use HTTP, never a 1 MiB websocket frame, for a historical document.

## Ordering and retries

All history operations use the room's ordered queue and live access source. List/preview do not
create an uncreated room as a side effect of a failed authorization. Creation's normal initial
capture is atomic with room creation. A list fails rather than serving a stale copied head.

Save and restore use durable caller/request identity and immutable body digests (lifecycle v1).
After access and role validation, resolve an accepted receipt before re-evaluating a now-expired
selected version or stale expected head. Same ID/different body gives 409 `request_id_reused`.
For a new request, unavailable version is 404; changed expected head is 409 `head_changed` and
changes nothing. A pending accepted restore returns 503 `restore_pending` with no success result;
Retry with exactly the same path/body checks/resumes it. An ordinary 503 without a proven rollback
is also uncertain to the browser. A confirmed rolled-back restore returns 503 `restore_failed`;
only this result permits the UI to say document/history were not changed. Invalid requests and
known pre-commit refusals never begin a restore. No automatic browser mutation retries.

Name is a last-ordered absolute metadata assignment; success returns canonical metadata.
Lost save/name answers retain the request/assignment for explicit retry and never show success
before confirmation. Failed canonical refresh retries the read, not a confirmed mutation.
Do not add deletion, Trash, purge or historical share routes. Browser board URL remains
`#/b/<boardId>`; Home remains `#/files`. Version selection is tab memory, not a new URL.
